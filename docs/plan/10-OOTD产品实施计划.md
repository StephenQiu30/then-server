## 2026-09-13项目全流程目标

用户本次明确要求以整个项目的 docs 为执行范围。总目标是贯通 **design → PRD → plan → implementation → tests/acceptance**：覆盖当前有效的设计 01–14、PRD 10–19、产品计划、实际存在的单切片计划和验收 10–19，按依赖逐项实施并以实际结果验收。旧生活管理文档只用于历史数据决策；研究提案不自动成为已批准需求。

当前先交付 Woo 式受控静态流程，并继续完成真实 3D 与本地闭环。AI 2.5D 和同步保持独立门禁；阶段结果不记作整个目标完成，具体顺序按本文件顶部当前用户决定。完成一个工具切片、完成文档审核、甚至通过一个发布层级，都只更新整体进度。整体目标持续有效，直到约定的目标范围逐项通过验收；若用户明确以某个发布层级作为终点，先记录范围决策，再按该层级判断完成。

### SMART执行与完成判定

| 维度 | 执行约束 | 可复核结果 |
| --- | --- | --- |
| S：具体 | 每项当前需求均定位到所属 design、PRD、近期切片或分期登记及 acceptance；切片内维护 spec 与 checklist，不另建重复事实源 | 下方全流程矩阵及各 FF-SS 需求/验收映射 |
| M：可衡量 | 当前发布范围需求追踪率 100%；必选验收全部通过；未关闭的发布阻断为 0；任何缺少结果的检查保持 pending/blocked | 需求 ID → 任务 ID → 测试/验收 ID → 环境、版本、命令与结果；文档数、生成文件数不作为功能完成率 |
| A：可执行 | 每次只推进一个具备输入的最小切片任务；先复现缺陷，再做根因修复和相关回归；不预建远期表、模块、服务或兼容层 | 切片同一时间最多一项 in_progress；未具备输入的任务明确关闭条件，不编造批准、资产或测试证据 |
| R：相关 | 每项实现必须支持无上传内置三维主路径、真实衣橱/推荐/记录/删除闭环或分期 Woo 照片增强，或已登记的阶段范围 | 无关重构、旧功能扩展和未批准云功能不混入当前交付 |
| T：有检查点 | 每个近期切片在开工前写明时间盒、本轮结束条件和检查点；每次任务结束回写证据，超出时间盒时记录原因和下一次检查条件 | 当前检查点归 12-03/16-01 剩余验收及 11-02/16-02 合同；已解除的构建/旧数据阻断不重复作为前置。缺少设备、资产、发布决策时不虚报整体完成日期 |

### 每个切片开始代码前必须具备

1. 所属功能与稳定需求 ID、明确非目标、用户输入/成功/失败/取消/恢复状态。
2. 领域实体所有权、约束、版本、删除与历史保留；需要 API 的切片必须完成 OpenAPI，纯本地切片明确无 API 变更。
3. 精确依赖和资产版本、真实模型/供应商输入、权限与媒体路径；相关高风险 POC 有结论。
4. 迁移与回滚、性能/容量/输入上限、测试夹具与可执行验收步骤。
5. 一份同文件统一契约、任务、状态、证据的 `FF-SS` 执行计划，契约获批后编码。现在不为未来功能批量创建占位计划。

后端合入证据必须覆盖 [Design 02 测试与合入检查](../design/02-后端架构.md#测试边界)，首版发布增加 OOTD-SYS-ACC-012/013；本次新增验收均 pending。

原 M0–M6 编号保留，历史任务与批准记录不重编号。M1–M3 承接真实角色/直接换装与本地数据闭环，11-02 已批准并进入实现；M4 按 Woo 决定前移，M5 条件动态与多设备同步继续分期。本人 OOTD 批量拆分不作为单件图/手工计划的前置，同步不隐含包含在静态试穿里。

## 风险与缓解措施

| 风险 | 缓解措施 |
| --- | --- |
| 旧代码未跟踪或包含未保存成果 | 迁移前建立可恢复提交/分支；只成组清理，保留 Git 证据 |
| 把旧开发数据豁免用于未来 OOTD 数据 | 本次仅退役旧开发实现；未来衣橱 migration、删除和恢复独立验收，不做启动自动清库 |

| AI 生成改变人物或衣物细节 | 授权测试集、内容安全、质量门、诚实免责声明和一键反馈 |
| 队列重复造成重复计费或迟到结果复活 | 幂等键、Outbox/Inbox、租约、fencing token、删除 tombstone |
| 技术栈一次引入过多运维复杂度 | 按阶段启用；本地核心不运行后端，云生成才启用完整运行栈 |
| 图片与穿着规律泄露 | 端侧净化、私有存储、短签名、最小日志、目的分离与删除审计 |

## 发布与回滚

- 用户已确认旧开发数据不保留，19-02 已完成旧入口/源码退役；本地 M1/M2 不再等待旧发布盘点，首份 OOTD schema 按 12-01 契约建立。
- M1–M3 本地部分可独立验收，具备发布证据后可作为阶段交付；它不等于当前 Woo 流程加真实三维的整体目标完成。云入口必须由服务端能力与 feature flag 双重门控。
- M4 先内部和小流量灰度，限制并发、日成本、单用户配额和供应商地域；删除演练未通过不得扩大流量。
- M5 使用独立开关，关闭后静态试穿、推荐与保存仍可用。
- 数据 migration 使用 expand/contract；发布前建立数据库与对象恢复点，不在同一版本执行不可逆旧数据删除和大规模 UI 切换。
- 不为旧 App、旧字段或旧接口增加兼容层；回滚不得清除新旧用户数据，也不承诺旧二进制可以读取新 schema。涉及持久数据的切片须明确恢复点、可重放修复或同 schema 修复版本，并以实际演练证明恢复；历史数据保留是数据正确性要求，不能被“无兼容处理”解释为清库授权。
