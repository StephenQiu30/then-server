## 范围

把已确认的技术选型转化为可构建、可测试的 iOS 与 Go 最小工程。此计划不实现记账、日历或出行业务，也不提前选择云厂商；国内地图与云 OCR 已明确不进入当前实现。

## 里程碑

1. 固定工具链、依赖和架构边界。
2. 创建可构建的 iOS 原生工程和可启动的单进程 Go 服务。
3. 打通 OpenAPI 生成、Swagger、PostgreSQL schema 和 contract test。
4. 对日历、定位、通知、导航和 OCR 做真机技术验证。
5. 在 P0 PRD 与领域模型批准后进入业务开发。

## 实施顺序

先创建最小 iOS 和 Go 工程，再打通契约与数据库，最后做系统能力 POC。业务 Feature 只能依赖已验证的 Service/Repository 协议，不应在 POC 前直接绑定第三方 SDK。

Go 依赖只在出现真实 import 时写入 `go.mod`；不得为了“看起来完整”提交未使用依赖。Swift 依赖则在 Xcode 工程创建时以 Exact requirement 落地，由 `Package.resolved` 固定解析结果。

## 风险与缓解措施

- Xcode 26.6 CI 需要 macOS Tahoe 26.2 或更高版本：创建 CI 前确认 runner 镜像，不使用 beta Xcode。
- iOS 18 的位置、日历和通知行为无法只靠模拟器证明：每个 POC 保留真机系统版本、设备与证据。
- 单一 `schema.sql` 不能表达所有复杂线上数据转换：P0 限制 Atlas Community 管理的对象范围，首次复杂变更前重新评审。
- MapKit 可能无法返回部分路线：保留手动出发时间、复制地址和返回计划，不以覆盖率或第三方地图选择阻塞发布。
- 中文票据 OCR 准确率未知：建立脱敏基准集，所有结果必须人工确认。

## 发布与回滚

- 技术基线文档与版本文件可以通过 Git 回滚；依赖升级必须同时回滚锁文件。
- iOS 工程首次发布前可以调整本地 schema；一旦有用户数据，只能通过 GRDB 有序 migration 演进。
- PostgreSQL 空库可重建；非空环境变更前必须有备份/PITR、dry-run、数据转换、验收与回滚计划。
- 云厂商未批准前，不发布依赖其密钥、SDK 或隐私清单的构建；当前构建不得包含国内地图或云 OCR SDK。
