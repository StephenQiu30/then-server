# 衣橱归档恢复与状态筛选后端执行计划

## 状态与范围

- 对应 `BL-WARDROBE-01`、`WARDROBE-REQ-005/006/011` 与 `WARDROBE-ACC-005` 的服务端子集；本片 `approved / completed（后端开发范围）`。
- 当前用户已确定后端先行，故只修改 `then-server/backend` 与关联 Design、PRD、Acceptance 文档；Web/App 管理界面、离线本地库和真机发布验收不在本片。
- 复用现有衣橱 CRUD、revision、计划/实际快照和服务端增量同步。不会新增媒体、旅行上下文、状态历史事件表或推荐算法。

## MVP 合同

1. `wardrobe_items.archived_at` 是独立生命周期事实。`NULL` 表示 `active`，非空表示 `archived`；归档不覆盖 `availability`，恢复也保留当时的 `wearable/laundry/lent_out/packed` 值。
2. `GET /wardrobe/items` 默认只返回 active 衣物；支持 `lifecycle=active|archived|all` 和可选 `availability=wearable|laundry|lent_out|packed`。筛选在 owner 条件和游标判断中同时生效，游标指向不属于当前筛选的衣物时返回 404，不静默跳过。
3. `POST /wardrobe/items/{item_id}/archive` 与 `POST /wardrobe/items/{item_id}/restore` 接受 `{expected_revision}`，成功返回更新后的衣物。命令严格校验当前 revision；重复的当前状态或过期 revision 返回 409。归档/恢复各自递增 revision、写入 `updated_at` 与 `sync_changes`。
4. 新计划和实际穿着快照读取衣橱时，归档衣物一律拒绝作为新选择；待洗、借出和未匹配上下文的已打包衣物继续遵循既有确认合同。已有计划/实际的最小文字快照不因后续归档、恢复或可用性编辑而改写。
5. `WardrobeItem` 与 HTTP 响应新增 `archived_at` 与 `lifecycle`；创建仍只能产生 active 衣物，普通 `PUT` 可修改名称、类别、可用性和确认属性但不改变归档生命周期。数据导出包含当前 `archived_at`。
6. 实际数据库仍由 GORM record 与集中 `AutoMigrate` 生成；运行时 Huma OpenAPI 是唯一接口 schema。不得把 active 默认列表误称为完整管理 UI，也不为未来状态审计预建空表。
