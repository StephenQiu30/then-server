# 主动同步合同执行计划

## 状态与边界

- 对应 `BL-SYNC-01`、`OOTD-REQ-014`、`SYNC-REQ-001～005`、`SYNC-ACC-001`。本地合成数据技术合同 `approved / completed`；`BL-SYNC-02～04` 和生产启用均 `pending`。本片只改文档，不新增 API、表或 App 功能。
- 复用当前 Cookie owner、客户端 UUID、各实体 revision/幂等创建与现有本人 CRUD。当前首版离线 Look、本地衣橱、推荐和记录不因本合同自动上云；账号登录、媒体上传、生成与同步是独立动作。

## 已核对的服务端事实

`wardrobe_items` 有 owner/UUID、revision、幂等创建和分页，但删除后无墓碑；`outfit_plan_deletions`、`wear_event_deletions`、`diary_entry_deletions` 已阻止同 ID 迟到重建，尚无可供第二设备读取的统一变更水位。反馈使用事件 ID 与命令回执。衣橱删除可修订/删除计划与实际；实际改变会重算计划状态；计划或实际删除会解除日记引用；媒体删除会修订日记。只记录直接 CRUD 将漏掉这些连带变化。

## 固定合同

1. **启用范围与归属**：用户在客户端按当前账号主动启用一组结构化范围：衣橱、计划、实际穿着及反馈、私人日记；本阶段无逐领域开关。访客事实只留本机，登录不触发上传；导入时用户逐批确认归属，保留本地 UUID 作为远端 UUID，同 owner 冲突才明确选择新 UUID 并在客户端保存映射。换账号使用独立映射、游标和缓存，旧账号迟到结果不得写入新账号。未实现的服务端 Look、未授权媒体字节、推荐推断、帖子/社区和生成任务不在本轮同步范围；媒体引用若存在只表达服务端关联，媒体读取/传输另立用途合同。
2. **增量事实**：新增每 owner 事务水位与 `(owner_id,seq)` 变更记录；每条只含实体类型 `wardrobe_item/outfit_plan/wear_event/wear_feedback/diary_entry`、ID、`upsert/delete`、可空实体 revision 和 seq，不复制正文或媒体 key。一次业务事务对所有 owner 可见变更写入同一日志，包括前述连带修订与删除；同内容幂等重试不产生新 seq。水位行在业务事务内串行分配 seq 并持锁至提交，不能用可能逆序提交的独立 PostgreSQL sequence 或客户端时间当游标。
3. **初始与分页**：`GET /sync/changes?after=<owner绑定游标>&limit=1..100`；省略 `after` 表示从 0 初始化，响应 `changes`、`next_cursor`、`has_more`，只返回 active 本人范围并 `Cache-Control: no-store`。游标是版本化、包含 owner UUID 与 seq 的不透明编码，不是凭据；跨 owner、损坏、未来水位拒绝，不静默从头或跳过。首次启用前的现有远端记录与计划/实际/日记墓碑须进入一次性、可重试的 owner 种子；衣橱从本切片实施起补墓碑，既往已物理删除且无记录的衣物不能虚构历史。变更记录和墓碑在本地合成开发范围随账号存续，不设假定的生产清理 TTL；删号级联清理。生产保留/升级另评审。
4. **应用变更**：客户端按 seq 顺序拉取并在一轮完成前暂存，按类型调用现有本人 GET 读取当前值；较旧 revision/seq 不覆盖已取得的新值。若旧 upsert 的详情因后续删除已为 404，继续读取后续 delete 事件，不把 404 当新建授权。仅在本机事务应用完页后持久化游标，断网重拉允许重复事件；完整拉取结束才展示一致的已同步状态。服务端写入继续调用现有单实体接口及 expected_revision，409/404 保留待处理草稿并由用户复核，不做时间戳胜出或万能 bulk 合并。
5. **删除优先**：衣橱需补 owner/ID 墓碑；已有计划/实际/日记墓碑保持。删除与变更记录同事务提交，迟到同 ID create/update 无法复活；用户确需重新建立时明确创建新 UUID 并复核关联。删除衣橱时按既有历史策略传播受影响计划/实际；删除计划/实际和媒体时传播日记/计划连带修订。账号删除先撤销访问与会话，再清理 owner 变更流；离线设备不能靠旧游标重新上传已删账号内容。
