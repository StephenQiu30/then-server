本文是 10 号总 PRD 的功能拆分，不替代总 PRD。基础推荐必须本地、结构化且独立于数字形象和视觉生成成立。

## 背景与问题

用户的问题不是缺少更多穿搭图片，而是在有限时间内从自己真正拥有、今天确实可穿的衣物中做出决定。无限推荐流、不可解释的“AI 适合你”和视觉上好看但现实不可执行的结果，会增加选择负担并削弱信任。

产品需要先尊重用户明确约束，再根据场合、天气、活动和穿后反馈提供少量、差异明确的方案。用户应能理解推荐原因、看到不确定信息、锁定满意部分并只替换一件；无权限、无照片、离线和视觉生成失败都不能阻断决定。

## 目标用户

- 希望减少每天出门前穿搭决策时间的用户。
- 已录入至少一条完整可穿路径，希望提高已有衣物利用率的用户。
- 对场合、天气、步行量或特定单品有明确约束的用户。
- 不提供人物照片、不授权日历或位置、或经常离线使用的用户。
- 希望逐步个性化，但不接受身体、人口属性或消费能力推断的用户。

## 产品目标

1. 在衣橱具备完整可穿路径时，用户从进入“今日”到选定一套方案的中位时间不超过 90 秒。
2. 每次默认最多提供三套方向明确、可直接执行的方案；数量不足时如实展示。
3. 所有候选只使用用户真实拥有且当前可用的衣物，并先满足用户硬约束。
4. 每套方案提供可理解的理由和关键不确定性，用户可以锁定单品、局部换件并撤销。
5. 无照片、无日历、无精确位置、无网络和视觉生成失败时，基础推荐、调整与保存仍完整可用。
6. 只从用户主动确认的实际穿着，或在独立反馈动作中明确提交且可撤回的结构化反馈渐进学习；不从身体、外貌、人口属性、消费历史或生成媒体操作推断偏好。

## 非目标

- 不推荐用户未拥有的商品，不把购物、广告、品牌或联盟链接混入候选。
- 不预测或保证真实尺码、合身、垂坠、透明度、保暖数值或医学冷热风险。
- 不评价显瘦、遮缺陷、年龄感、吸引力、肤色、身体或社会地位。
- 不让静态试穿、动态预览或生成图美观程度参与基础过滤和排序。
- 不读取完整日历正文、参会人、精确地址、路线、联系人、账单或购物历史。
- 不提供无限信息流、连续随机重抽或以不确定奖励延长使用时长的机制。
- 首发基础推荐不依赖远程大模型、云端排序或外部推荐服务。
- 不在本功能中创建衣物、纠正衣物事实或记录实际穿着。
- 首发不提供静态或动态生成媒体的下载、导出、社交分享和公开链接。

## 功能范围

### 首发必备能力

- 用户通过结构化控件确认日期时段、场合、正式度、室内外、活动量、步行量、天气与体感偏好；未知项可以保留未知。
- 不授权日历或位置时提供完整手工输入；普通推荐不要求精确位置。
- 使用用户当前衣橱中已确认、当前可用的真实衣物生成完整穿搭路径。
- 先应用用户明确排除、已锁定单品、着装要求和用户声明的天气/活动硬约束，再进行排序。
- 默认展示最多三套：稳妥、天气优先和更有风格；无法形成三套时展示真实数量。
- 每套显示具体理由、证据来源和关键不确定性，不展示容易造成虚假精确感的总分。
- 支持锁定单品、只换一件、更暖、更凉、更正式、更休闲、更轻便和手工替换。
- 会话内调整可撤销；未保存浏览、跳过、查看或保留生成结果不自动写成长期偏好。
- 无可行组合时说明缺少类别、不可用状态或冲突约束，并一次只提供一个明确放宽选项。
- 保存前重新检查衣物状态和版本；发生变化时由用户选择替换、恢复状态或保留为计划。
- 天气不可用或过期时显示更新时间，允许使用缓存或手工天气。
- 基础生成、解释、调整和保存可离线完成；无数字形象时使用单品拼图或结构化清单。

### 后续或条件能力

- 用户可关闭的天气、日历或城市级位置上下文增强。
- 自然语言生成结构化场景草稿；结果必须由用户确认，不能直接选择衣物或排序。
- 经独立价值、隐私和架构评审的云端排序增强。
- 静态 AI 试穿与动态预览；仅消费用户已选结构化方案，不反向改变推荐事实。
- 由实际穿着和明确反馈形成的渐进个性化策略。

条件能力不可用时，结构化本地路径和手工输入必须保持完整。

## 核心用户故事

- 作为用户，我可以手工说明今天的场合和天气，不需要授权日历、照片或精确位置。
- 作为用户，我只能看到自己真实拥有且当前可穿的衣物，不会出现虚构商品。
- 作为赶时间的用户，我可以比较最多三套方向明确的方案，而不是浏览无限列表。
- 作为有明确要求的用户，我可以指定必须防雨、必须正式或必须穿某件，系统不会暗中放宽。
- 作为用户，我可以知道方案为什么适合、哪些衣物属性或上下文仍不确定。
- 作为用户，我可以锁定喜欢的上装，只换鞋或让剩余部分更暖，并随时撤销。
- 作为衣橱不足的用户，我可以知道缺少哪个类别并快速添加或改为手工搭配。
- 作为离线或无照片用户，我可以完成生成、调整和保存，不被引导去开启云能力。
- 作为用户，我的衣物状态变化后，系统会在保存前提醒，而不是静默替换我的选择。
- 作为重视隐私的用户，我的身体照片、完整日程和消费信息不会进入推荐。
- 作为用户，我知道保存方案只形成 `OutfitPlan`；只有我主动确认日期并选择“实际穿了”后，系统才形成 `WearEvent`。
- 作为用户，我可以单独提交并撤回穿后反馈；仅保留一张静态或动态生成结果不会被理解为我偏爱这套穿搭。

## 业务规则

| 需求 ID | 规则 |
| --- | --- |
| `RECOMMEND-REQ-001` | 候选中的每个衣物都必须来自当前用户衣橱，并保留可验证的稳定身份。 |
| `RECOMMEND-REQ-002` | 归档、待洗和借出衣物默认不得进入新推荐；已打包衣物仅在用户明确匹配的上下文中可用。 |
| `RECOMMEND-REQ-003` | 推荐先执行硬约束，再排序；不得为凑足候选数量让高分抵消约束失败。 |
| `RECOMMEND-REQ-004` | 已锁定单品与硬约束冲突时必须说明冲突，不得自动解锁或忽略约束。 |
| `RECOMMEND-REQ-005` | 未经用户确认的属性不能成为硬过滤事实；未知信息降低确定性并明确展示。 |
| `RECOMMEND-REQ-006` | 每次最多展示三套差异化候选；无法形成足够差异时减少数量，不复制方案。 |
| `RECOMMEND-REQ-007` | 推荐理由只能引用用户输入、衣物确认属性、当前状态、已批准上下文或明确反馈，不能使用空泛的“AI 认为适合”。 |
| `RECOMMEND-REQ-008` | 数字形象、人物照片、外貌、身体、年龄、肤色、性别、消费能力和品牌价格不得参与推荐资格或排序。 |
| `RECOMMEND-REQ-009` | 基础推荐不等待或依赖静态、动态视觉生成；生成失败不能改变结构化方案。 |
| `RECOMMEND-REQ-010` | 局部换件只改变未锁定角色；替换项仍需满足当前全部硬约束。 |
| `RECOMMEND-REQ-011` | 衣物状态或场景在生成后发生变化时，已保存内容不被静默覆盖；保存前必须复核并让用户决定。 |
| `RECOMMEND-REQ-012` | 未保存浏览、跳过和预览失败不自动等于负面偏好；只有用户主动确认的实际穿着，或在独立反馈动作中明确提交且仍可撤回的结构化反馈，才能进入长期学习。 |
| `RECOMMEND-REQ-013` | 日历、天气或位置只提供用户可确认的最小摘要；原始日程正文和精确位置不得进入基础推荐。 |
| `RECOMMEND-REQ-014` | 离线、无照片、无权限和上下文不完整时必须保留手工输入、基础推荐、换件和保存。 |
| `RECOMMEND-REQ-015` | 保存推荐或手工方案只创建 `OutfitPlan`；只有用户主动确认日期并选择“实际穿了”才创建 `WearEvent`，两者不得由浏览、收藏或生成行为互相推导。 |
| `RECOMMEND-REQ-016` | 查看、放大、保留、删除或重新生成静态/动态结果只表达对媒体或本次预览的操作，不是穿搭偏好；若要学习，必须另设目的明确、可撤回的反馈动作。 |
| `RECOMMEND-REQ-017` | 首发不提供生成媒体下载、导出、社交分享或公开链接，相关入口不得作为推荐转化指标。 |

## 用户可见状态与失败恢复

| 状态或失败 | 用户看到 | 恢复路径 |
| --- | --- | --- |
| 衣橱不足 | 缺少的完整路径或类别，不伪造方案 | 快速添加、无图新增或手工搭配。 |
| 场景不完整 | 未知项和可能影响 | 手工补充或继续生成低确定性候选。 |
| 天气过期或离线 | 最近更新时间，不冒充实时天气 | 使用缓存、手工选择或稍后刷新。 |
| 正在生成 | 有限进度和已过滤衣物，不展示虚假结果 | 取消并转手工搭配。 |
| 只有一至两套 | 真实数量及无法形成更多差异的原因 | 选择现有方案、调整约束或补充衣物。 |
| 无可行候选 | 缺少类别、不可用状态或具体约束冲突 | 一次修改一个约束、改变状态、快速添加或手工组合。 |
| 锁定项冲突 | 冲突单品和冲突规则 | 明确解锁、修改约束或保持当前手工方案。 |
| 衣物状态已变化 | 受影响单品和变化信息 | 替换、恢复状态或保留为计划，不静默处理。 |
| 推荐超时或失败 | 原衣橱与场景仍完整 | 有限重试或手工组合；不进入无限加载。 |
| 视觉预览失败 | 结构化方案、理由和拼图保留 | 重试预览、直接保存或继续换件。 |
| 历史偏好不足 | 使用通用规则并说明尚未个性化 | 继续使用；实际穿着和反馈后渐进改善。 |

## 成功指标及防误导指标

北极星指标：**推荐后实际穿着，且用户认为温度与场合基本合适的搭配比例。**

### 成功指标

- 具备完整衣橱路径的用户，从打开“今日”到选定方案的中位时间。
- 推荐直接采用率、实际穿着率、平均替换件数和从推荐到保存的完成率。
- 最多三套方案中至少一套被采用或经局部调整后采用的比例。
- 推荐理由被展开后促成选择或有效调整的比例。
- 无可行方案用户通过修改一个约束、改变状态或快速添加后完成决定的比例。
- 天气过期、离线、无照片和无权限场景下完成推荐与保存的比例。
- 衣物状态竞态在保存前被正确发现并恢复的比例。
- 实际穿着后的温度、舒适与场合合适反馈改善趋势。

### 防误导与护栏指标

- 不把浏览候选、查看试穿图、收藏或保存计划计为实际穿着。
- 不通过暗中放宽硬约束、重复同一方案或混入未拥有商品提高候选数和采用率。
- 无照片、无日历和离线用户的基础推荐完成率必须单独监测，不能被平均值掩盖。
- 跳过、关闭页面、视觉生成失败以及查看或保留生成结果不得自动计为喜欢或不喜欢这套。
- 不以延长浏览时长、连续刷新次数或无限推荐消费量作为成功指标。
- 推荐理由准确率、未知信息展示率和状态竞态漏检率必须作为信任护栏。
- 任何包含身体、人口属性或消费能力推断的推荐都属于发布阻断事件。

## 依赖与风险

- 依赖衣橱提供稳定衣物身份、用户确认属性和及时的现实可用状态。
- 渐进建库会产生未知属性，需要在可用性与确定性之间诚实平衡。
- 天气缓存、手工场景和未来上下文增强可能互相冲突，需要用户确认优先。
- 大衣橱组合数量可能影响响应时间；超时必须有手工路径而非无限等待。
- 用户反馈稀疏或含义模糊，错误学习可能固化单一风格或把偶然选择当偏好。
- “更有风格”等方向可能形成审美偏见，理由必须基于可解释规则且允许忽略。
- 衣物状态可能在推荐、换件与保存之间变化，需要阻止无提示保存。
- 远程模型或自然语言能力可能编造衣物与理由，因此只能作为条件增强，不能控制核心决策。

## 发布门禁

- 在无网络、无照片、无日历与无位置权限时，手工场景、基础推荐、局部调整和保存可完整执行。
- 所有候选衣物均可追溯到当前用户衣橱，归档、待洗、借出和不匹配的已打包状态按规则排除。
- 硬约束、锁定项、未知属性和无可行组合具有可验证且不误导的处理。
- 候选最多三套且方向可区分；衣橱不足时如实减少数量，不复制或虚构商品。
- 每个理由和不确定性都可追溯到用户输入、已确认衣物或明确规则，文案不存在身体和人口评价。
- 局部调整只改变未锁定角色，撤销可靠，保存前能发现衣物状态变化。
- 目标最低支持设备上达到已批准的交互性能门槛；超时、取消和重复请求不会用旧结果覆盖新会话。
- VoiceOver、最大辅助字号、提高对比度和 Reduce Motion 下可以完成确认、比较、锁定、换件和保存。
- 静态试穿、动态预览和任何云端增强关闭或失败时，不影响结构化推荐与保存。
- 分析口径能够区分查看、计划、收藏和实际穿着，且不收集稳定衣物 ID、方案正文或敏感上下文。
- 推荐学习证据能够区分 `WearEvent`、独立且可撤回的结构化反馈和纯媒体操作；撤回反馈后停止将其用于后续学习。
