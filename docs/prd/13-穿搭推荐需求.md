# 穿搭推荐需求

更新：2026-09-30。状态：deferred / 未排期。上位需求：[10-OOTD产品需求](10-OOTD产品需求.md)，研究依据：[29-Woo虚拟人偶与自用成本决策](../design/29-Woo虚拟人偶与自用成本决策.md)。

本轮目标是本人自用的每日穿搭记录与 Woo 式虚拟人偶展示。首版通过拍摄当日穿搭、手工类别和手工选衣确定组合；推荐算法、天气/日历/位置增强、锁件软排序与自动偏好学习不再是首版前置。本文保留旧推荐合同的稳定身份供追溯，不承诺实施日期，不认领旧候选截图、后端或测试已完成本轮体验。

## 当前产品关系

今日 / 衣橱 / 穿搭簿必须在没有推荐器、天气服务、定位、日历、账号或后端时完成拍照/手工选衣、保存日期、收藏、编辑删除、离线查看和同套资产复用。手工选衣由 [12-数字衣橱与衣物录入需求](12-数字衣橱与衣物录入需求.md) 定义，Look、计划、实际穿着和反馈由 [16-穿搭记录与反馈需求](16-穿搭记录与反馈需求.md) 定义。

手工选择不叫“AI 推荐”；生成满意人偶图片或模型不表示方案适合天气、实际合身或已经穿过。保存 Look 不默认创建计划，保存计划不计入实际穿着，收藏/旋转/导出不推导长期偏好。首版不出现需要联网却无法完成的推荐入口或“正在个性化”假状态。

## 将来重新启用时的流程与持久化原则

此节仅限定候选方案质量，不把延期功能列为首版必须完成：

1. 本人确认最小场景和硬约束；未知项保持未知，不授权天气/日历/定位也能手工继续。
2. 读取当前本地真实衣橱版本，先过滤再产生有限候选。无解说明缺类别、不可用状态或具体冲突，不捏造衣服、不悄悄放宽。
3. 锁件、换件和撤销仅作用于当前草稿；冲突保留草稿并明确由本人修改。
4. 明确保存前复核版本；保存的是计划快照，推荐候选本身不创建穿着、反馈或云生成。
5. 若另行启用个性化，允许本人关闭、纠正、撤回；只从仍有效的明确证据重建，删除后不能保留隐形偏好缓存。

| 情况 | 未来应有的恢复行为 |
| --- | --- |
| 无候选 / 衣橱不全 | 解释原因，直接转手工选衣或添加衣物；已有草稿保持。 |
| 天气不可用 / 过期 | 标注更新时间/未知，可手工确认；缓存不冒充实时数据。 |
| 候选计算取消 / 失败 | 回到原场景与选择，可重试，不写计划或偏好。 |
| 锁件冲突 / 无替代 | 展示冲突项，本人解锁或改约束，不自动改变。 |
| 保存时衣物已改/删 | 显示差异并重新确认，不部分提交，不复活已删条目。 |
| 反馈撤回 / 历史纠正 | 删去失效证据并重算，不继续引用旧偏好。 |

未来实施仍须本地稳定 ID、候选输入版本和幂等保存；视觉任务及费用由其所属 Look 管理，不由推荐器自动发起。扩展数据不得在本轮为未排期功能预建。

当前首版验收应证明：关闭/不存在推荐、天气、日历、定位及账号服务时，仍可完成三入口的手工核心旅程；页面不将手工选择或人偶生成标为推荐结果，也不把日期归档或收藏计为实际穿着/学习信号。
