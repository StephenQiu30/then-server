# 历史数据迁移需求

## 状态与上位需求

- 状态：`approved_principles`，2026-08-30；迁移原则已批准，旧生活管理数据的具体处置策略仍待产品确认。
- 本文是 [`10-OOTD产品需求.md`](10-OOTD产品需求.md) 的专项补充，专门承接其中“旧生活管理用户数据的导出、保留或删除策略”这一上线前待决项；只有具体策略和上线门槛全部确认后，该待决项才算关闭。
- [`../design/12-OOTD技术债清理与迁移设计.md`](../design/12-OOTD技术债清理与迁移设计.md) 负责在本文产品决策确定后约束迁移与清理实现；[`../design/10-OOTD服务端与异步任务设计.md`](../design/10-OOTD服务端与异步任务设计.md) 与 [`../design/11-OOTD权限隐私与安全设计.md`](../design/11-OOTD权限隐私与安全设计.md) 只提供云端边界、导出、删除和诚实状态的共同约束。
- 当前唯一允许在最终处置策略批准前推进的切片是 [`../plan/19-01-历史发布事实与数据盘点执行计划.md`](../plan/19-01-历史发布事实与数据盘点执行计划.md)。该计划当前为 `draft`；契约获批后也只授权只读盘点，不授权打开真实用户记录、执行 migration、改写或删除数据、切换入口或清理历史代码。
- 当前尚未确认旧生活管理版本是否曾向真实用户发布，也未确认是否存在真实用户本地数据。本文不得被解读为“已经存在已发布用户”的证据。
- 在具体处置策略、适用数据范围、用户文案、发布分期和验收证据全部批准前，不得据此删除、改写或自动重建旧数据。

## 背景与问题

“于是”已经从生活管理产品转向 C 端 OOTD 产品。仓库中仍保留记账、日历、出行、生活记录及其相关设置、权限和本地数据处理能力。新产品需要建立新的首页与数据闭环，但旧实现退出当前产品范围，不等于其中可能存在的数据可以直接删除。

目前缺少足够证据判断旧版本是否曾经发布、哪些版本可能产生数据、数据是否仍存在于设备或其他受控副本中。若在这一事实未关闭时直接替换入口、重建本地存储或移除历史读取能力，用户可能看到“数据消失”，即使底层字节仍在；若直接清理，又可能造成不可恢复的数据损失。相反，为规避风险而无限期保留但不给访问、导出和删除路径，也不是完整的产品承诺。

因此需要先定义面向用户的迁移契约：默认保护已有数据，允许只读访问和结构化导出，仅在用户明确选择后删除，并在升级失败时保留数据和提供恢复路径。具体采用何种历史入口、保留多久、哪些数据进入导出或删除，仍需根据发布与数据盘点结果作出产品决定。

## 目标用户

- 设备上可能存在旧生活管理数据、并升级到 OOTD 版本的用户。这里描述的是需要保护的潜在用户场景，不代表已经确认有真实发布用户。
- 希望暂时保留旧数据、稍后再决定如何处理的用户。
- 仍需查看历史记录，但不再需要继续创建或编辑旧生活管理内容的用户。
- 希望获得可自行保存、检查和迁移的结构化副本后再决定是否删除的用户。
- 全新安装或经可靠检查未发现旧数据、不应被迁移流程阻断的 OOTD 用户。

## 产品目标

1. 在没有明确用户授权的情况下，不删除、不覆盖、不自动重建可能承载旧生活管理数据的存储。
2. 对无法确认是否发布的情况按“已发布”风险等级处理，直到取得可审计的相反证据。
3. 让发现旧数据的用户可以保留数据、只读访问、结构化导出或明确删除，并理解每个选择的后果。
4. 让未立即作出选择的用户继续保留旧数据，不用删除换取 OOTD 核心功能。
5. 升级、读取或导出失败时保留原数据，提供可重复尝试的恢复路径，不以清空数据作为修复手段。
6. 将不可逆删除与大规模 UI 替换放在不同发布阶段，降低数据故障、入口变化和回滚困难叠加的风险。
7. 保护新建 OOTD 数据不受历史迁移失败影响，使旧数据处理与 OOTD 本地核心可以分别恢复。
8. 用可验证、不过度收集敏感信息的指标证明迁移安全，而不是只证明新页面能打开。

## 非目标

- 不把旧记账、日历、行程或生活记录自动转换为衣物、搭配、穿着反馈或推荐偏好。
- 不继续扩展旧生活管理功能，也不承诺在只读入口中恢复所有旧编辑和系统同步能力。
- 不在本文锁定数据库表、文件目录、迁移框架、导出实现库或云端部署方式。
- 不默认把旧数据上传云端、用于分析、用于模型训练或与新 OOTD 账号合并。
- 不通过更换 Bundle ID、要求用户卸载重装、启动时重建、隐藏旧入口或移除权限来绕过迁移决策。
- 不把缓存、临时文件和可重新获取数据等同于用户有意义的原始记录；各类别是否保留、导出或清理必须由数据盘点明确。
- 不保证恢复由用户主动卸载 App、抹掉设备或操作系统外部行为已经删除的数据。
- 不宣称已经存在真实发布用户、真实历史数据或已完成迁移。

## 功能范围

### 19-01 只读盘点许可

- 允许在 `19-01` 契约经产品、隐私、安全与发布负责人批准后，读取仓库源码、Git 历史、既有 migration 源码、工程配置，以及由有权负责人提供的最小非敏感发布或资源元数据。
- 盘点只形成发布事实、历史版本代码谱系、数据类别、潜在副本、新旧隔离与未知项清单；每条结论区分直接证据、交叉支持推断和未知。
- “只读”不包含查询或打开真实用户数据库、媒体、Keychain、备份、对象存储对象、供应商正文或支持工单正文；也不包含运行可能初始化、升级或写回数据库的旧 App。
- `19-01` 完成只允许形成 `GO-BASELINE-PLANNING`、`GO-PROTECTION-PLANNING` 或 `NO-GO-EVIDENCE` 的后续规划结论，不表示迁移、只读访问、导出、删除、入口替换或生产发布已获批准。
- 任何会创建、修改或执行 migration，改写 schema 或记录，移动或删除历史代码、资源、媒体、缓存或用户数据，改变发布控制面，或读取真实用户正文的动作，都必须停止并等待后续独立策略与执行计划批准。

### 适用数据

在发布门槛关闭前，迁移范围至少要盘点并分类：

- 用户主动创建或确认的旧生活管理记录及其必要关系、时间、时区、金额单位和用户可见备注。
- 为旧功能保存的用户偏好、分类和状态，只在其有独立用户意义时纳入保留或导出。
- 从系统日历、位置或其他系统能力导入、缓存或派生的数据；需区分权威来源、用户补充内容与可重新获取副本。
- 旧功能可能产生的本地媒体、导出文件或其他派生内容；是否存在以及是否仍有用户价值必须通过盘点确认。
- 认证凭据、密钥、诊断信息、缓存和临时数据等不应直接进入用户导出的内部内容；其保留与清理由安全和隐私评审单独确认。

每一类数据都必须得到“保留、只读展示、结构化导出、明确删除、无需迁移但可安全重建”中的一项或多项批准结论。没有结论的数据按保留处理，不得因无法识别而删除。

### 发布事实分支

| 已确认场景 | 产品处理原则 |
| --- | --- |
| 有充分证据证明旧版本从未面向真实用户发布 | 可在保留工程快照和完成测试数据盘点后采用新的 OOTD 数据基线；不需要伪造面向用户的迁移流程 |
| 已确认发布，且历史数据仍需访问 | 保留旧数据，提供只读访问和结构化导出；新的 OOTD 数据不得复用旧业务语义 |
| 已确认发布，且产品拟停止保留历史数据 | 先提供发布说明、可用的只读或导出路径和明确用户选择，再执行可验证删除 |
| 无法确认是否发布 | 按已发布处理；不删除、不改写、不自动重建，并满足本文全部用户保护要求 |

“从未发布”必须有可审计证据，不能仅依据当前团队记忆、没有客服反馈、仓库中没有发布配置或尚未发现数据来推断。

### 用户选择

发现旧数据后，产品必须支持以下能力。它们并非四个互斥按钮：用户可以先保留或只读查看，再导出，最后另行选择删除。

#### 保留

- 未选择、跳过、关闭页面、离线或迁移流程异常时，默认保持旧数据不变。
- 用户可以明确选择“暂时保留”，稍后从稳定入口重新查看可用选项。
- 保留不等于允许永久隐藏。若当前版本暂时只能保护数据而尚未提供完整只读能力，界面必须说明现状、可恢复路径和后续处理方式。
- 后续若要结束保留或只读支持，必须提前提供明确通知和有效导出窗口；不得静默删除。

#### 只读访问

- 用户可以查看有意义的历史记录、主要关系和必要展示语义，但不能新增、编辑或重新启动旧系统同步。
- 只读入口必须明确标注“历史数据”，避免用户误认为旧生活管理功能仍在维护。
- 拒绝旧权限、系统来源暂不可用或 OOTD 云端能力不可用时，已经安全保存在本地的可读内容仍应尽可能可访问。
- 只读展示不得悄悄修改历史记录，也不得把旧数据作为 OOTD 推荐输入。

#### 结构化导出

- 用户可以在删除前或独立于删除操作发起导出；成功导出不会自动删除 App 内数据。
- 发起前展示将包含与不包含的数据类别、预计记录数量或范围、敏感性提示和失败后的保留行为。
- 导出结果必须使用有文档说明、可由通用工具继续处理的结构化格式，并带导出版本、生成时间、数据类别、记录计数及必要的时区、币种或单位语义。
- 无法导出的记录、缺失关系或损坏内容必须在结果摘要中明确列出，不能以静默跳过后仍宣称“完整导出”。
- 导出只在用户选择的本地或系统分享路径中交付，不因导出自动上传到产品云端。导出包不得包含令牌、密钥、内部诊断正文或没有用户意义的实现细节。
- 低存储、系统中断或生成失败时保留旧数据，允许用户释放空间或稍后重试。

#### 明确删除

- 删除必须由用户从历史数据入口主动发起，不预选、不与使用 OOTD、接受协议、退出旧页面或完成导出捆绑。
- 确认前以用户可理解的类别展示删除范围、不可恢复后果、仍可能等待到期的副本类型，以及先导出的入口。
- 模糊手势、关闭入口、长期未使用、撤回系统权限或未在期限内作答均不构成删除授权。
- 删除请求接受后，界面区分“正在删除”“删除未完全完成”和“删除完成”；不能把请求已提交、入口已隐藏或本地部分已清理称为全部完成。
- 如果盘点发现本地之外还存在旧数据、备份或其他受控副本，删除范围与完成时限必须单独说明并验证；在尚未证明存在这些副本前，也不得声称已经有云端旧数据。
- 删除过程中部分失败时，不恢复已经删除的内容来伪造一致状态，也不宣称完成；保持安全状态、继续恢复或提供人工处理路径。

### 与 OOTD 发布的关系

- 全新安装或可靠检查未发现旧数据时，用户直接进入 OOTD，不显示虚假的迁移任务。
- 发现旧数据不应阻止用户使用不依赖历史数据的 OOTD 本地核心；历史数据入口和处理状态仍必须可找回。
- 大规模 OOTD 根界面替换与任何会执行不可逆历史数据删除的能力不得进入同一个发布版本。前一阶段必须先证明数据保持、入口可达和恢复有效，再批准后一阶段。
- 新 OOTD 数据与旧生活管理数据在产品语义上隔离。旧数据迁移失败、只读入口故障或导出失败不得清空、回滚或污染用户已经创建的衣橱与穿搭。

## 核心用户故事

- 作为可能从旧版本升级的用户，我希望 App 先确认并保护旧数据，而不是在第一次打开时自动清空或重建。
- 作为暂时不想决定的用户，我可以跳过迁移选择并继续使用 OOTD，旧数据仍被保留且以后可以找回处理入口。
- 作为仍需要历史记录的用户，我可以只读查看旧内容，并清楚知道旧功能不再支持编辑。
- 作为希望自行留档的用户，我可以导出结构化副本，知道导出了什么、遗漏了什么，并在导出失败后安全重试。
- 作为希望清理数据的用户，我可以先导出，再明确选择删除，并看到诚实的处理进度和未完成原因。
- 作为不愿删除的用户，我不会因为拒绝删除而失去 OOTD 核心功能，也不会被反复强迫选择。
- 作为遇到升级故障的用户，我可以重试、进入可恢复的只读或导出路径，且 App 不会以重置数据作为默认修复。
- 作为全新用户，我不会被与自己无关的历史迁移页面阻断。

## 业务规则

### 数据判断与默认行为

- **MIGRATION-REQ-001 发布未知保护**：无法确认旧版本是否发布时按已发布处理，直到取得经评审的相反证据。
- **MIGRATION-REQ-002 默认保留**：任何没有明确用户删除选择的路径都保留旧数据；未知、无法解析和暂时损坏不等于可删除。
- **MIGRATION-REQ-003 先盘点后处置**：先建立数据类别、来源、用户意义、敏感级别和副本范围清单，再批准对应的保留、访问、导出和删除行为。
- **MIGRATION-REQ-004 新旧隔离**：旧生活管理记录不自动转化为 OOTD 事实，也不影响新 OOTD 数据的可用性和完整性。
- **MIGRATION-REQ-005 无暗黑模式**：保留或稍后决定与删除具有同等可见性；不得通过默认选项、倒计时、重复打扰或功能惩罚诱导删除。

### 访问、导出与删除

- **MIGRATION-REQ-006 只读真实性**：只读访问保持历史值和必要展示语义，不在打开、排序或展示时写回业务内容。
- **MIGRATION-REQ-007 导出可验证**：只有结构、计数、必要语义和完整性检查通过且结果成功交付后，才能记为导出完成；导出失败不改变原数据。
- **MIGRATION-REQ-008 删除显式性**：删除需要单独、清晰的主动确认；导出成功、卸载提示、权限撤回或不再访问都不能替代删除授权。
- **MIGRATION-REQ-009 删除完整性**：只有批准范围内的主数据及已确认副本均达到公开承诺后，才能显示删除完成；备份等待到期或部分失败必须如实展示。
- **MIGRATION-REQ-010 敏感保护**：历史数据、导出文件和处理状态按其内容的最高敏感级别保护，不进入日志、分析或测试夹具的正文。

### 升级、失败与发布

- **MIGRATION-REQ-011 升级失败保留**：非删除迁移的任一步失败都不得自动清空数据。用户重新启动或重试后应从安全检查点恢复，或进入保留数据的恢复页面。
- **MIGRATION-REQ-012 删除失败不伪装回滚**：明确删除开始后的部分失败继续显示处理中或需要处理，不恢复已经删除的数据，也不提前显示完成。
- **MIGRATION-REQ-013 可重复执行**：系统杀进程、低存储、重复打开、重复操作或版本重试不能产生重复记录、重复删除或状态倒退。
- **MIGRATION-REQ-014 发布隔离**：不可逆历史数据删除和大规模 UI 替换不得同版发布；每一阶段都有独立停止条件、恢复路径和观察窗口。
- **MIGRATION-REQ-015 恢复优先**：发现异常时优先停止进一步改写并保留数据；“重置 App”只能作为用户已导出且明确选择删除后的结果，不能作为故障排查步骤。

## 用户可见状态与失败恢复

| 用户可见状态 | 必须表达的含义 | 可用动作与恢复 |
| --- | --- | --- |
| 正在检查历史数据 | 尚未得出结论，不能展示成“没有数据” | 等待、稍后重试；不得开始删除或重建 |
| 未发现历史数据 | 当前可靠检查未发现适用数据，不代表已删除过数据 | 进入 OOTD；提供问题反馈入口 |
| 已发现，待选择 | 数据已受保护，尚未决定长期处理方式 | 暂时保留、只读查看、导出、了解删除 |
| 已保留 | 当前不删除，用户可稍后回来 | 继续 OOTD、只读查看、导出或另行删除 |
| 历史数据只读 | 可以查看，但旧功能不再编辑或同步 | 浏览、导出、返回；读取失败不修改数据 |
| 正在导出 | 正在准备结构化副本，原数据仍保留 | 等待、取消安全退出、稍后恢复 |
| 导出完成 | 结果已通过完整性检查并成功交付 | 打开或分享、再次导出、返回；不自动删除 |
| 导出失败 | 结果未完整交付，原数据未因此删除 | 查看安全错误说明、释放空间、重试或寻求帮助 |
| 删除待确认 | 尚未执行不可逆处理 | 查看范围、先导出、取消或明确继续 |
| 正在删除 | 已接受明确请求，但所有副本尚未验证完成 | 查看进度；已删除内容不重新开放 |
| 删除未完全完成 | 仍有范围未处理或等待恢复，不能宣称完成 | 自动重试、查看公开时限或联系支持 |
| 删除完成 | 批准范围已验证完成；若有备份等待期则单独说明 | 查看非敏感完成摘要并继续 OOTD |
| 升级失败，可恢复 | 新版本无法安全读取或推进，旧数据仍被保留 | 重试、在可行时只读/导出、提交不含正文的诊断信息 |

错误信息只说明用户可采取的动作和稳定错误类别，不显示底层存储名称、敏感正文或可能泄露生活记录的诊断细节。若恢复能力暂不可用，应明确说明数据仍在保护中，而不是展示空白历史列表。

## 成功指标及防误导指标

### 安全与用户结果指标

- 未经明确选择的历史数据删除事件数：目标为 0。
- 已覆盖历史版本样本中，升级或检查失败后原始数据仍可恢复的比例：发布门槛为 100%。
- 只读入口对已声明支持的数据类别正确展示的比例，以及失败后无写入的比例。
- 结构化导出通过格式、记录计数、必要语义和完整性验证的比例；同时统计明确披露的不可导出记录数。
- 删除请求按公开范围完成的比例、超时数、部分失败数和删除后重新出现事件数。
- 用户从“发现历史数据”到完成其自主选择的比例与中位时间，但未选择并继续保留不视为失败。
- 升级后报告“历史数据丢失”“无法访问”或“导出不完整”的用户问题率，并区分确认缺陷、使用误解和外部设备删除。
- 新 OOTD 本地核心在历史迁移处于保留、失败或恢复状态时仍可完成的比例。

指标只记录完成证明、数据类别、版本、状态和非敏感错误类别，不采集历史记录正文、导出内容或可还原个人生活规律的细节。

### 禁止的误导性口径

- 不能把迁移页面已展示、用户点击选项或后台任务已开始记为迁移成功。
- 不能把导出文件开始生成、存在临时文件或弹出系统分享面板记为完整导出。
- 不能把删除请求已提交、入口已隐藏、本地部分已清理或用户卸载 App 记为端到端删除完成。
- 不能把“没有收到投诉”当作没有数据损失，也不能把“当前没发现发布记录”当作从未发布的证据。
- 不能把默认保留但没有访问、导出或后续说明的状态包装为迁移完成。
- 不能通过默认勾选删除、缩短决定时间、阻断 OOTD 或反复提醒来提高选择完成率。
- 不能把新 OOTD 激活、留存或穿搭创建数增长作为允许清理旧数据的替代证据。
- 不能把真实用户是否存在的未知状态从指标分母中排除；未知版本和未知数据按高风险分支单独报告。

## 依赖与风险

### 依赖

- 旧版本发布记录、Bundle/构建版本、分发渠道和可审计发布证据的盘点结论。
- 旧数据类别、来源、敏感级别、用户意义、关系和潜在副本的完整清单。
- 每个历史版本的合成或脱敏结构样本，以及损坏、中断、低存储和重复升级样本。
- 产品、隐私、安全、法务、客服与发布负责人共同批准具体保留、只读、导出和删除策略。
- 用户文案、结构化导出说明、隐私说明、本地化、VoiceOver 与最大 Dynamic Type 验收。
- 发布分期、观察窗口、停止条件、恢复责任人和用户支持路径。

### 主要风险

- 发布证据缺失导致错误采用“从未发布”分支，产生不可恢复删除。
- 数据盘点遗漏某个历史版本、用户自定义字段、关系或媒体，造成只读或导出不完整。
- 新根界面先移除旧入口，使数据虽保留却对用户不可访问。
- 升级在低存储、系统杀进程或局部损坏时中断，产生重复内容或真假不明的空状态。
- 旧系统权限被移除后，历史数据展示错误地依赖重新授权；用户拒绝权限不应成为删除理由。
- 导出包包含敏感生活记录，用户误分享到不安全位置；必须在交付前提示并避免默认上传。
- 删除只覆盖可见记录，遗漏派生内容、缓存、未知服务端副本或备份；在盘点未完成前不能承诺范围。
- 同版执行大 UI 替换与不可逆删除，发生问题时无法判断入口、读取还是数据本身失败。
- 只追求迁移完成率，诱导用户删除或忽略选择权，损害信任并形成合规风险。

## 待产品确认的具体策略

以下事项未批准，任一项缺失都不得执行历史数据不可逆处置：

1. 旧版本是否曾真实发布，以及证明“从未发布”所需证据的负责人和截止时间。
2. 每类旧数据是否保留、提供多久只读访问、是否进入结构化导出以及删除覆盖哪些副本。
3. 用户未作选择时的长期保留与历史入口支持周期，以及未来结束支持前的通知和导出窗口。
4. 结构化导出的具体格式、文件组织、字段说明、媒体范围、完整性证明和版本兼容承诺。
5. 明确删除的确认方式、可取消边界、完成时限、备份说明和部分失败支持流程。
6. 大 UI 替换与删除能力分别进入哪个发布阶段，以及两个阶段之间的观察窗口和停止条件。
7. 是否存在旧账号、服务端数据、备份或其他受控副本；若存在，需另行批准地域、身份匹配、导出和删除方案。
8. 面向潜在升级用户的发布说明、客服话术、故障补救和隐私政策更新。

在这些事项关闭前，产品默认策略只有“保留并冻结旧数据”，不等于已经批准长期只读方案，也不等于迁移完成。

## 发布门禁

历史数据相关发布必须同时满足：

1. 发布事实分支已有书面结论；无法确认时明确采用已发布保护分支。
2. 数据盘点覆盖所有已知历史版本，并为每类数据批准保留、只读、导出、删除或安全重建结论。
3. 具体产品策略、用户文案、保留时限、导出范围和删除范围通过产品、隐私、安全与法务评审。
4. 所有历史版本样本均能被正确识别；未知或损坏样本停止改写并进入可恢复状态。
5. 升级前后数据计数、关键关系、时间、时区、金额单位和用户可见内容通过一致性验证。
6. 只读、导出和明确删除分别完成正常、离线、低存储、系统杀进程、重复执行、局部损坏和版本重试验收。
7. 非删除迁移失败时，100% 的验收样本保留原数据并可恢复；不存在以自动重置作为恢复路径的实现。
8. 导出样本通过结构、计数、必要语义、完整性和敏感字段排除检查；导出失败不会改变原数据。
9. 删除确认无预选、无捆绑、范围可理解；处理状态不早于真实完成，部分失败和备份等待得到诚实展示。
10. 不可逆删除与大规模 UI 替换已安排在不同发布版本，前一阶段观察窗口、停止条件和恢复证据均已通过。
11. 历史入口在保留期内可发现、可访问，并通过 VoiceOver、最大 Dynamic Type、本地化与核心真机流程验收。
12. 使用合成或合规脱敏样本完成测试，不以真实用户数据、自动化旧报告或“没有投诉”替代发布证据。
13. 灰度、支持、异常升级停止、后续修复发布和非敏感诊断流程已有明确负责人。

以上是后续迁移或处置能力的发布门禁，不阻断已获批边界内的 `19-01` 只读盘点。`19-01` 自身只有在其契约状态由 `draft` 变为 `approved`、证据处理协议批准且全程零数据/控制面 mutation 时才能执行；它不能关闭第 2～13 项生产门禁。

任何门槛未通过时，可以继续开发不改动历史数据的 OOTD 本地功能，并可在 `19-01` 已批准只读边界内补充盘点证据，但不得发布会隐藏、改写或删除旧数据的变更。
