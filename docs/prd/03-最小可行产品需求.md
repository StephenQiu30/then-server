# MVP 产品需求

## 状态

草案，2026-08-09。本文用于确认产品范围和业务规则；P0 固定为单设备本地模式，账号、多设备同步与云厂商属于 P1，实施前仍需产品负责人单独批准。预算、长期原始轨迹、票据原图保存、Time Sensitive、国内地图适配和商业化不在当前范围。

## 背景与问题

个人的时间、出行和消费分别散落在日历、地图、支付工具和记账 App 中，用户需要反复录入同一件事，却仍难以回答“今天要去哪里、什么时候出发、这次出行花了多少”。现有工具之间也不存在可以稳定读取第三方导航历史或个人支付流水的通用接口。

“于是”不尝试替代所有工具，而是成为个人生活信息的组织层：用户先在一个清晰、可控的本地空间完成记账和行程准备，再按需把系统日历、路线规划、外部导航和实际消费连接起来。

## 目标用户

- 使用 iPhone、需要记录日常消费并进行基础收支复盘的个人用户。
- 日程中经常包含线下地点，希望获得出发提醒和导航衔接的用户。
- 重视隐私、希望断网仍可使用，并且不愿把完整账单、日历或轨迹默认上传到云端的用户。
- 初期主要面向中国大陆生活场景；路线与导航只使用 Apple 地图并按系统能力尽力提供，不承诺城市或交通方式覆盖率。

## 产品目标

1. 用户可以在 15 秒左右完成一笔常见支出或收入记录，并始终看清资金从哪里来、到哪里去。
2. 用户可以把系统日历事件或手动输入转换为出行计划，获得可解释的出发时间、提醒和导航入口。
3. 用户可以主动记录实际行程，并将交通、停车、餐饮等消费与本次行程关联。
4. 核心能力在无网络、未登录和拒绝非必要权限时仍有可恢复路径。
5. 任何 OCR、日历导入、路线估算或同步结果都不会绕过用户确认直接修改已确认账务。

## 产品原则

- **本地先行**：用户操作先可靠写入本地数据库，网络和账号不是记账与结束行程的前置条件。
- **渐进授权**：日历、通知、定位、相机和相册只在用户触发对应功能时申请，不在首次启动集中索取。
- **来源可见**：手动、日历、OCR、导入和同步生成的信息都显示来源和更新时间。
- **确认优先**：外部信息先成为建议或草稿，用户确认后才进入正式账本或行程。
- **真实边界**：交接到 Apple 地图后不宣称已经同步其导航过程；路线信息不自动变成实际消费。
- **可撤回**：权限、同步和行程记录都能单独关闭；临时轨迹与票据图片按明确生命周期自动删除。

## 功能范围

### P0：MVP

| 领域 | 能力 |
| --- | --- |
| 今天 | 展示今日事件、下一次出行、待处理草稿和本月收支摘要；提供全局快速新增入口。 |
| 记账 | 账户与分类管理；支出、收入、同币种转账、退款/冲销；交易列表、详情、搜索和月度汇总。P0 不实现预算。 |
| 票据识别 | 使用端侧 OCR 生成待确认草稿；图片只在识别会话内临时使用，确认、取消或会话结束后删除，不提供保存原图。设备不支持或识别失败时回退到相册选择和手动输入。OCR 不作为发布阻塞项。 |
| 日历 | 用户主动开启后读取选定系统日历；默认缓存过去 30 天至未来 90 天；正确处理时区、全天和重复事件。 |
| 出行计划 | 从日历地点或手动输入创建计划；确认起终点、交通方式、出发缓冲、路线快照和预计到达时间。 |
| 提醒与导航 | 通过普通本地通知提供出发提醒；只支持 Apple 地图基础调起，不承诺城市、交通方式或路线覆盖率，不实现 Time Sensitive 与国内地图适配。 |
| 实际行程 | 用户明确开始后临时采集位置以生成本次行程摘要；显示进行中状态，支持手动结束和异常恢复。摘要确认成功后删除原始轨迹点，只保留起止时间、耗时、距离和完整性。 |
| 生活关联 | 关联日历事件、出行计划、实际行程与交易；行程结束后可快速补记交通及相关消费。 |
| 设置与隐私 | 权限状态、日历来源、定位记录、数据导出、数据删除、诊断信息和关于页面。 |

P0 固定采用单设备本地模式，不以账号、Go 后端或网络作为发布依赖。领域模型和 Repository 边界保留后续接入能力，但 P0 不创建伪登录、伪同步或不可用云备份入口；Sign in with Apple 与多设备同步进入 P1。

### P1：增强

- Sign in with Apple、账户/交易/用户确认计划/Journey 摘要的跨设备增量同步与账号删除；不包含票据图片或原始轨迹。
- CSV/XLS 等用户主动选择的账单文件导入、截图批量识别、重复检测和导入报告。
- 更丰富的趋势、商户分析、出行费用模板和异常消费提示。
- 路况变化后的提醒重算、常用地点、通勤模板和行程费用复盘。

### P2：扩展

- 衣橱、单品信息、穿搭记录和基于日程/天气/场景的穿搭建议。
- 智能生活复盘、跨领域洞察和用户明确触发的推荐。
- 任何社交、家庭共享或协作账本能力。

穿搭是独立领域，不进入记账与出行 P0 的发布关键路径；在独立 PRD 确认图片权限、推荐依据、内容安全和模型成本前，不实现模型或上传衣物照片。

## 核心用户故事

### 快速记账

- 作为用户，我可以选择支出、收入或转账，输入金额、账户、分类和时间后保存。
- 作为用户，我可以离线保存交易，并立即在余额和报表中看到一致结果。
- 作为用户，我可以对误记交易进行编辑；若交易已被同步或关联，我能看见修改影响并使用退款/冲销保留历史。

### 日历到出行

- 作为用户，我可以选择允许读取哪些系统日历，并预览将被读取的字段和时间范围。
- 作为用户，我可以把带地点的事件转换为出行计划；地点是自由文本时，我会先确认解析结果。
- 作为用户，我能看见 MapKit 路线来源、计算时间、预计耗时和缓冲时间，并能手动调整出发时间。
- 作为用户，日历权限被拒绝时仍可手动创建同样的出行计划。

### 提醒、导航与实际行程

- 作为用户，我可以为计划启用出发提醒；通知权限被拒绝时，App 会显示明显状态而不是假装已提醒。
- 作为用户，我可以从“于是”当前已支持且设备已安装的导航 App 中选择；P0 为 Apple 地图，调起失败时可以复制地址。
- 作为用户，我可以主动开始记录实际行程，并随时看见、暂停或结束记录。
- 作为用户，从 Apple 地图返回后可以确认“已到达”或“结束行程”；App 不依赖地图回传到达状态。
- 作为用户，我在确认行程摘要前可以看见轨迹是否完整；确认后 App 删除原始轨迹，只保留摘要。

### 行程与消费关联

- 作为用户，我可以从行程摘要快速新增交通、停车、餐饮等交易。
- 作为用户，我可以把已有交易关联或解除关联到行程，而不会改变交易本身的会计含义。
- 作为用户，我可以查看一次行程的计划、实际耗时、距离和相关消费汇总。

## 业务规则

### 记账

- 正式交易使用交易与分录模型；每种币种的分录合计必须为零。
- 金额使用整数最小货币单位和 ISO 币种，不使用浮点数。
- 首次进入账本时离线创建单一 LocalProfile、系统账户、默认现金账户和内置分类；系统地区只用于建议本币，用户必须在发布第一笔正式交易前确认。
- 转账不计入收入或支出；退款引用原交易并在报表中抵减对应分类。
- 正式交易更正必须在一个数据库事务中以原交易为根创建相反分录和替代交易；完整冲销也必须与原交易状态、回执及版本更新原子提交，不能通过隐藏旧分录改变账本事实。
- OCR、文件导入和外部建议只生成待确认草稿；草稿不影响余额和正式报表。
- 用户确认的交易不得被外部同步、分类建议或重复导入静默覆盖。

### 日历

- 只读取已经进入 iOS 系统日历数据库且用户选中的日历，不承诺读取第三方 App 私有日历。
- EventKit 标识符不是永久业务主键；系统需要处理事件移动、重复、修改、取消和重新导入。
- 全天事件默认不生成出发提醒；用户明确添加时间和地点后才可转为普通出行计划。
- 日历变化可更新来源字段，但不得覆盖用户已经手动修改的出行字段；冲突时要求用户选择。
- 原始 EventKit 身份、CalendarOccurrence 及事件关系默认只存在本机；未来账号同步只上传用户确认后的计划，不以系统日历授权替代云上传同意。

### 路线、导航和轨迹

- 路线结果是带 MapKit 来源、WGS-84 坐标系、计算时间和有效期的快照，不代表最终实际路线。
- Apple 地图交接是单向的，不读取其导航历史、偏航、到达状态或收藏。
- 精确轨迹只在用户主动开始后临时记录；停止、权限撤回或系统限制时保存已有片段以完成摘要。摘要确认后立即删除原始点，不提供长期保留、导出或云备份。
- 预计交通费用只能作为草稿建议，不能自动写入正式交易。

### 离线、同步和删除

- 本地写入成功即视为用户操作成功；同步状态单独展示，不用网络错误否定本地结果。
- 每次可同步变更携带全局唯一 mutation ID、实体版本和设备信息；服务端必须幂等。
- 账务和用户编辑过的出行冲突不使用静默 last-write-wins。
- 删除通过 tombstone 同步；用户执行完整删除时必须覆盖主数据、派生数据和待处理队列。

## 成功指标

指标采集必须先通过隐私评审；未接入分析平台时可用脱敏、本地聚合和可选用户研究验证。

| 目标 | 建议指标 |
| --- | --- |
| 快速记账 | 常见手动交易从点击新增到保存的中位时间不超过 15 秒；保存成功率不低于 99.5%。 |
| 日历转出行 | 已授权且包含有效地点的事件中，成功创建出行计划的比例；地点确认失败率。 |
| 提醒可信 | 普通本地提醒的调度成功率、权限拒绝可见率、过期路线被重新确认的比例。 |
| 行程闭环 | 已完成行程中有关联消费或明确选择“无消费”的比例。 |
| 数据质量 | OCR 草稿确认率、重复导入拦截率、账务不平衡错误为零。 |
| 稳定性 | 核心流程崩溃率、数据库写入失败率、活跃行程意外中断恢复率。 |

## 依赖与风险

- EventKit 读取需要 Full Access，授权文案和无授权路径会直接影响启用率。
- MapKit 路线不可用时必须允许手动设置出发时间并复制地址；当前版本不设置城市、交通方式或覆盖率发布门槛。
- 后台定位受系统调度、权限和耗电影响，必须用真机和真实移动场景验收。
- 端侧中文票据 OCR 的字段准确率未知，必须建立脱敏样本集；手动输入始终保留。
- 单一 `schema.sql` 适合 P0 声明式结构，首次处理复杂生产数据演进前必须重新评估迁移策略。
- P1 引入账号与同步前，需要同时解决中国大陆云资源、隐私政策、账号删除、RPO/RTO 和运营主体问题。

## 已关闭的范围决策

以下项目不再作为当前版本的未决问题，也不进入 P0/P1 实施计划：

1. 不设置 Apple 地图城市或交通方式覆盖门槛，不接入高德、百度、腾讯等国内路线或导航适配器；路线失败走手动降级。
2. 不长期保留原始轨迹；用户确认行程摘要后立即删除原始点，异常恢复只保留到行程完成或丢弃。
3. 不实现预算、结转、多币种预算或共享预算；保留单币种账户、分类统计和基础月度收支报表。
4. 不保存票据原图，不提供票据附件或云备份；OCR 图片仅在识别会话内临时存在。
5. 不启用 Time Sensitive 或 Critical Alerts；出发提醒只使用普通本地通知。
6. 不实现付费、订阅、免费容量、权益分层或购买入口；若未来需要商业化，必须新建独立 PRD，不从当前范围推导。

## 发布门槛

- 记账、日历到出行、实际行程和消费关联四条主路径均有可执行验收。
- 拒绝日历、通知、定位、相机或网络访问时均存在清晰的手动或只读降级路径。
- 不存在读取第三方支付流水或导航历史的误导文案。
- 数据导出、删除、权限撤回和敏感日志检查通过。
- 所有不在当前范围的预算、附件、长期轨迹、国内地图、特殊通知和商业化能力均不得留下伪入口、空表或临时 SDK。
