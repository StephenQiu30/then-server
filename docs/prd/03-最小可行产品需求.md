# MVP 产品需求

## 状态

P0 范围已批准并实施中，2026-08-11。本文用于固定产品范围和业务规则；P0 固定为单设备本地模式，账号、多设备同步与云厂商属于 P1，实施前仍需产品负责人单独批准。预算、长期原始轨迹、票据原图保存、Time Sensitive、国内地图适配和商业化不在当前范围。实现进度与实测结论分别以 [`../plan/03-最小可行产品实施计划.md`](../plan/03-最小可行产品实施计划.md) 和 [`../acceptance/03-最小可行产品系统验收.md`](../acceptance/03-最小可行产品系统验收.md) 为准，不在本需求文档中用部分实现改写完整发布范围。

## 背景与问题

个人的时间、出行和消费分别散落在日历、地图、支付工具和记账 App 中，用户需要反复录入同一件事，却仍难以回答“今天要去哪里、什么时候出发、这次出行花了多少”。现有工具之间也不存在可以稳定读取第三方导航历史或个人支付流水的通用接口。

“于是”不尝试替代所有工具，而是成为个人生活信息的组织层：用户先在一个清晰、可控的本地空间完成记账和行程准备，再按需把系统日历、路线规划、外部导航和实际消费连接起来。

## 目标用户

- 使用 iPhone、需要记录日常消费并进行基础收支复盘的个人用户。
- 日程中经常包含线下地点，希望获得出发提醒和导航衔接的用户。
- 重视隐私、希望断网仍可使用，并且不愿把完整账单、日历或轨迹默认上传到云端的用户。
- 初期主要面向中国大陆生活场景；路线与导航只使用 Apple 地图并按系统能力尽力提供，不承诺城市或交通方式覆盖率。

## 产品目标

1. 用户可以在 15 秒左右完成一笔常见支出或收入记录，并始终看清资金从哪里来、到哪里去。
2. 用户可以把系统日历事件或手动输入转换为出行计划，获得可解释的出发时间、提醒和导航入口。
3. 用户可以主动记录实际行程，并将交通、停车、餐饮等消费与本次行程关联。
4. 核心能力在无网络、未登录和拒绝非必要权限时仍有可恢复路径。
5. 任何 OCR、日历导入、路线估算或同步结果都不会绕过用户确认直接修改已确认账务。

## 产品原则

- **本地先行**：用户操作先可靠写入本地数据库，网络和账号不是记账与结束行程的前置条件。
- **渐进授权**：日历、通知、定位、相机和相册只在用户触发对应功能时申请，不在首次启动集中索取。
- **来源可见**：手动、日历、OCR、导入和同步生成的信息都显示来源和更新时间。
- **确认优先**：外部信息先成为建议或草稿，用户确认后才进入正式账本或行程。
- **真实边界**：交接到 Apple 地图后不宣称已经同步其导航过程；路线信息不自动变成实际消费。
- **可撤回**：权限、同步和行程记录都能单独关闭；临时轨迹与票据图片按明确生命周期自动删除。

## 功能范围

### P0：MVP

| 领域 | 能力 |
| --- | --- |
| 今天 | 展示今日事件、下一次出行、待处理草稿和本月收支摘要；提供全局快速新增入口。 |
| 记账 | 账户与分类管理；支出、收入、同币种转账、退款/冲销；账本页提供月份切换、月度汇总、canonical root 交易列表、详情和本地搜索。P0 不实现预算。 |
| 票据识别 | 用户可拍照或通过系统照片选择器选择单张票据，端侧 OCR 生成当前记账表单内的待确认候选；采用候选只预填表单，用户再次保存后才入账。图片仅作为一次内存识别输入，识别返回、失败或取消后释放，不提供原图、附件或候选持久化。设备不支持或识别失败时保留手动输入。OCR 不作为发布阻塞项。 |

票据隐私说明必须出现在照片选择与相机操作之前，明确“仅用于本机本次识别，不保存或上传”，在标准字号和最大辅助字号下均可完整换行读取。两种字号的 UI 验收都必须滚动到说明本身，校验完整文案、位于两个图片操作之前且无文本裁切，不得用未出现说明的初始视口截图代替。
| 日历 | 用户主动开启后读取选定系统日历；默认缓存过去 30 天至未来 90 天；正确处理时区、全天和重复事件。 |
| 出行计划 | 从日历地点或手动输入创建计划；确认起终点、交通方式、出发缓冲、路线快照和预计到达时间。 |
| 提醒与导航 | 通过普通本地通知提供出发提醒；只支持 Apple 地图基础调起，失败后可由用户显式复制已确认目的地并返回计划。不承诺城市、交通方式或路线覆盖率，不实现 Time Sensitive 与国内地图适配。 |
| 实际行程 | 用户明确开始后临时采集位置以生成本次行程摘要；显示进行中状态，支持手动结束和异常恢复。摘要确认成功后删除原始轨迹点，只保留起止时间、耗时、距离和完整性。 |
| 生活关联 | 关联日历事件、出行计划、实际行程与交易；行程结束后可快速补记交通及相关消费。 |
| 设置与隐私 | 权限状态、日历来源、定位记录、数据导出、数据删除、诊断信息和关于页面；生产界面、App 名称与系统权限用途说明提供一致且完整的简体中文文案。 |

P0 固定采用单设备本地模式，不以账号、Go 后端或网络作为发布依赖。领域模型和 Repository 边界保留后续接入能力，但 P0 不创建伪登录、伪同步或不可用云备份入口；Sign in with Apple 与多设备同步进入 P1。

### P1：增强

- Sign in with Apple、账户/交易/用户确认计划/Journey 摘要的跨设备增量同步与账号删除；不包含票据图片或原始轨迹。
- CSV/XLS 等用户主动选择的账单文件导入、截图批量识别、重复检测和导入报告。
- 更丰富的趋势、商户分析、出行费用模板和异常消费提示。
- 路况变化后的提醒重算、常用地点、通勤模板和行程费用复盘。

### P2：扩展

- 衣橱、单品信息、穿搭记录和基于日程/天气/场景的穿搭建议。
- 智能生活复盘、跨领域洞察和用户明确触发的推荐。
- 任何社交、家庭共享或协作账本能力。

穿搭是独立领域，不进入记账与出行 P0 的发布关键路径；在独立 PRD 确认图片权限、推荐依据、内容安全和模型成本前，不实现模型或上传衣物照片。

## 核心用户故事

### 今天与本地控制

- 作为用户，我可以在“今天”同时看到今日事件、下一次出发、未收口行程、本月收支和真实待处理项，不需要在多个页面重复查找。
- 作为用户，日历未授权、报表暂时读取失败或其他单个数据块不可用时，我仍能看到其他已保存信息并使用手动记账、建计划和恢复行程。
- 作为用户，我可以通过固定的“今天、账本、日程、行程、我的”五个一级入口找到所有 P0 能力，权限拒绝不会让入口凭空消失。
- 作为用户，我可以在“我的”了解当前权限、数据位置、票据与轨迹的保留规则，且不会看到不可用的账号、同步、云备份或订阅假入口。
- 作为用户，我可以在“我的”看到 App 名称、版本与构建号、单设备本地数据模式和诊断收集是否启用，以便反馈问题时只提供必要的版本信息。
- 作为用户，我可以从“我的”导出一份结构化 JSON，读取账户、正式账务、计划、行程摘要和消费关系；文件不会包含票据图片、日历来源身份、原始轨迹或内部安全字段。
- 作为用户，我可以单独清理日历缓存、删除已收口 Journey，或二次确认后删除本机全部数据，并在操作前明确看到哪些数据会保留。
- 作为简体中文用户，我在生产界面、App 名称和系统权限弹窗中看到一致、可理解且不截断关键含义的中文文案；任何缺失文案都不会退化为空白、内部标识符或未经审核的英文。

### 快速记账

- 作为用户，我可以选择支出、收入或转账，输入金额、账户、分类和时间后保存。
- 作为用户，我可以从独立的“还款”入口选择还款资产账户和信用卡账户；还款只改变账户余额，不被当作新的收入或支出，没有信用卡时我会得到可执行的建账引导。
- 作为用户，我可以离线保存交易，并立即在余额和报表中看到一致结果。
- 作为用户，我可以对误记交易进行编辑；若交易已被同步或关联，我能看见修改影响并使用退款/冲销保留历史。
- 作为用户，我在流水中只看到每笔业务交易的当前结果，并可从详情查看其原始记录、退款、冲销和更正历史，而不会被系统生成的会计行干扰。
- 作为用户，我可以切换月份查看收入、支出、净变化、支出分类排行和截至该月的最近六个月支出趋势；没有交易的月份也会以零值保留在趋势中。
- 作为用户，我可以组合资金账户、收入/支出分类、是否关联行程，以及商户、备注或完整金额条件筛选本地流水与月报，并一键清除全部条件；归档项目仍可用于查历史。

### 日历到出行

- 作为用户，我可以选择允许读取哪些系统日历，并预览将被读取的字段和时间范围。
- 作为用户，我可以把带地点的事件转换为出行计划；地点是自由文本时，我会先确认解析结果。
- 作为用户，我从普通事件进入表单时可看到事件标题、时间和地点初值；只有我确认目的地后才能保存，且保存计划不会修改系统日历事件。
- 作为用户，我从全天事件创建计划时，必须显式确认具体到达时间后才能保存或开启提醒；该时间属于我的计划值，不会被后续日历扫描静默覆盖。
- 作为用户，我能从日程事件或“今天”的待处理项查看来源旧值、新值和当前计划值，并明确选择保留计划或进入确认页采用变化。
- 作为用户，我在采用来源变化前可以重新确认标题、目的地、到达/出发时间、路线和提醒；如果计划或来源在我确认期间再次变化，App 会要求重新加载而不是覆盖较新的内容。
- 作为用户，我能看见 MapKit 路线来源、计算时间、预计耗时和缓冲时间，并能手动调整出发时间。
- 作为用户，日历权限被拒绝时仍可手动创建同样的出行计划。

### 提醒、导航与实际行程

- 作为用户，我可以为计划启用出发提醒；通知权限被拒绝时，App 会显示明显状态而不是假装已提醒。
- 作为用户，我可以从“于是”当前已支持且设备已安装的导航 App 中选择；P0 为 Apple 地图。调起失败时，我能看见本次目的地，并且只有在我点击“复制目的地”后 App 才写入剪贴板。
- 作为用户，如果我选择“开始记录并打开 Apple 地图”且地图失败，已创建的 Journey 仍可恢复；返回计划后仍能复制该计划的目的地。
- 作为用户，我可以主动开始记录实际行程，并随时看见、暂停或结束记录。
- 作为用户，从 Apple 地图返回后可以确认“已到达”或“结束行程”；App 不依赖地图回传到达状态。
- 作为用户，我在确认行程摘要前可以看见轨迹是否完整；确认后 App 删除原始轨迹，只保留摘要。
- 作为用户，定位被拒绝、暂时不可用或 App 意外中断时，我能看见记录停在何处，并选择继续、以部分/无轨迹摘要结束或丢弃；App 不会自动猜测已到达。

### 行程与消费关联

- 作为用户，我可以从行程摘要快速新增交通、停车、餐饮等交易。
- 作为用户，我可以把已有交易关联或解除关联到行程，而不会改变交易本身的会计含义。
- 作为用户，我可以查看一次行程的计划、实际耗时、距离和相关消费汇总。
- 作为用户，交易更正、退款或冲销后，原行程关联仍然存在，费用汇总自动体现不可变分录的最新净影响，不需要重复关联替代交易。

## 业务规则

### 记账

- 正式交易使用交易与分录模型；每种币种的分录合计必须为零。
- 金额使用整数最小货币单位和 ISO 币种，不使用浮点数。
- 首次进入账本时离线创建单一 LocalProfile、系统账户、默认现金账户和内置分类；系统地区只用于建议本币，用户必须在发布第一笔正式交易前确认。
- P0 支持现金、银行卡、电子钱包和信用卡账户，以及收入/支出分类；分类最多一层父子关系。账户和分类只允许归档与恢复，归档后仍保留历史数据但不能用于新交易；父分类归档后必须先恢复父分类再恢复子分类，普通管理流程不硬删除。
- 账户余额必须从全部 `posted` 分录重建：资产/支出按借减贷，负债/收入/权益按贷减借；负余额不得被绝对值或缓存掩盖。
- 转账不计入收入或支出；退款引用原交易并在报表中抵减对应分类。
- “信用卡还款”作为记账页独立可选的用户语义，保存时仍创建 `transfer`：来源只能是可用资产账户，目标只能是可用信用卡负债账户，不选择分类且不计入收入或支出；没有信用卡时提示先创建账户。
- 正式交易更正必须在一个数据库事务中以原交易为根创建相反分录和替代交易；完整冲销也必须与原交易状态、回执及版本更新原子提交，不能通过隐藏旧分录改变账本事实。
- 退款只从当前有效支出发起，可多次部分退款；已被冲销的退款不占用累计可退额度。存在有效退款时不允许直接整笔冲销支出，更正后的支出金额不得低于有效退款合计。
- 退款、冲销和更正必须校验用户看到的 root revision；陈旧页面提交不得覆盖更新后的交易链，重复命令标识也不得产生第二份影响。
- 流水以 canonical root 折叠展示当前有效版本；已撤销交易仍可查且明确标记，详情必须展示全部不可变历史和当前可退金额。退款、撤销与更正只能从详情中按当前状态开放，版本冲突时不得丢失用户输入或静默重试。
- 账本页必须直接提供月份切换、基础月报、近期交易和搜索；“今天”的本月摘要仅是只读概览，不能替代账本页。
- 本地搜索按当前有效版本匹配商户、备注或完整金额并保持 root 折叠；基础月报按用户时区的自然月从全部正式分录聚合本币收入、支出、净变化和支出分类，退款抵减支出、更正相互抵消、转账不计收支。
- 账本筛选可组合一个资金账户、一个收入/支出分类和“全部/已关联行程/未关联行程”；搜索词与这些条件共同作用于流水和月报，条件必须可见且可一次清除。筛选匹配当前有效交易与稳定 canonical root 行程关系，不允许更正前旧字段重新命中。
- 月报趋势固定为截至所选月份最近六个自然月的支出净额并补齐零月份；月份只限制月报与趋势，不能把用户的跨月本地流水搜索静默限制在当前月。筛选命中的 root 仍按期间内全部正式分录计算退款、冲销和更正净影响；选择分类时只统计该分类。
- OCR、文件导入和外部建议只生成待确认草稿；草稿不影响余额和正式报表。P0 单张票据候选仅存在于当前记账表单，必须显示金额、商户、日期、币种、订单号的识别状态与低置信度提示；采用后仍需用户保存。模糊重复只提示，不自动拦截或合并。
- 用户确认的交易不得被外部同步、分类建议或重复导入静默覆盖。

### 日历

- 只读取已经进入 iOS 系统日历数据库且用户选中的日历，不承诺读取第三方 App 私有日历。
- 首次日历授权后所有来源默认不选中；只有用户明确选择的来源才进入事件查询和本地缓存。权限撤回、账户暂不可用或取消选择来源不能被展示为事件已删除。
- EventKit 标识符不是永久业务主键；系统需要处理事件移动、重复、修改、取消和重新导入。
- 全天事件默认不生成出发提醒；用户明确添加时间和地点后才可转为普通出行计划。
- 只有当前状态为有效或暂未发现的本地事件才提供“创建出行计划”；已取消、已移出窗口、已确认删除或身份不明的事件不能直接创建。
- 事件地点文本只预填搜索，不等于已确认目的地。用户必须选择 MapKit 候选或明确使用当前文字地址；无地点时仍可填写手动目的地。
- 普通事件的未编辑到达时间保留事件来源；用户改动后记为用户值。全天事件的具体到达时间一经显式确认就必须记为用户值，即使确认后数值没有改变。
- 事件来源计划的目的地、计划、提醒期望状态和本地事件关系必须一次保存；关联事件失效或任一写入失败时不得留下部分计划。
- 计划保存时记录用户采用的事件来源版本。后续日历扫描只更新来源快照与待处理变化，不推进计划或关系中的采用版本，也不覆盖已确认的标题、地点、到达/出发时间和提醒状态。
- P0 事件来源计划的提醒默认不跟随来源。日历变化可更新来源字段，但不得自动重算或重新调度；需要用户比较来源新值与计划值后显式选择。
- “来源已变化”必须提供可达的处理入口；Today 待处理项与日程事件行打开同一份 revision，不得只显示无法清除的数量或徽标。
- P0 产品入口对同一 occurrence 只创建一个出行计划；重复操作应打开既有计划或返回明确提示，不产生第二个关系。历史异常重复关系不得被静默合并或批量覆盖。
- “保留当前计划”只解决用户已看到的来源 revision，不改变计划、地点、路线、提醒或采用版本；后续新 revision 仍重新进入待处理。
- “采用到计划”必须经过编辑确认页。提交时校验来源版本、关系采用版本和计划版本；陈旧页面、非连续 revision、已完成/取消计划或任一数据库失败都保持 revision 待处理且不产生部分更新。
- 采用新的时间或地点会使旧路线快照失效；用户必须重新计算路线或确认手动出发时间。提醒只按用户在确认页的选择重新安排，调度失败需保留计划并显示可恢复状态。
- 历史计划的标题来源不能用字符串相等推断，升级后按用户值处理；新事件计划只有用户未编辑事件标题时才可标记为事件来源。
- 原始 EventKit 身份、CalendarOccurrence 及事件关系默认只存在本机；未来账号同步只上传用户确认后的计划，不以系统日历授权替代云上传同意。

### 路线、导航和轨迹

- 路线结果是带 MapKit 来源、WGS-84 坐标系、计算时间和有效期的快照，不代表最终实际路线。P0 新快照在前台按 15 分钟新鲜期提示，过期或无路线时仍允许用户确认手动出发时间。
- 用户在地图搜索不可用时可以确认纯文字目的地并保存计划；从安装过旧版地点表结构的构建更新后，该能力仍必须可用。升级不得删除或重建旧账务、已保存的带坐标地点、计划、路线、提醒、Journey 或正式关系，也不得要求用户清空 App 数据才能继续。
- Apple 地图交接是单向的，不读取其导航历史、偏航、到达状态或收藏。
- Apple 地图打开失败必须绑定原 TripPlan 显示降级操作。地址去除首尾空白后非空时复制地址，否则复制地点名称；不复制坐标、时间、内部 ID 或其他上下文。
- 地图失败、列表刷新或打开记录页都不得自动写入剪贴板。只有明确点击复制按钮才写入，写入后显示“目的地已复制”。
- P0 不读取、解析或保存用户剪贴板原有内容，不在地址后追加营销文案、短链、坐标或追踪参数。
- 精确轨迹只在用户主动开始后临时记录；停止、权限撤回或系统限制时保存已有片段以完成摘要。摘要确认后立即删除原始点，不提供长期保留、导出或云备份。
- P0 只在用户点击开始时申请 When In Use 定位，不请求 Always；记录中必须始终存在明显状态和停止入口。同一设备只能有一个未收口行程，新建前必须恢复、完成或丢弃已有行程。
- 每个可用定位样本必须先以单调序号和初始质量标记落盘，再进行精度或跳点判断；过滤不得删除用于异常恢复的临时原始点。暂停、异常中断后继续或收尾后重新采集时，必须建立新片段并把完整性标为 partial。
- 结束记录只进入摘要复核，不立即宣称完成。只有在一个本地事务中完整验证摘要、删除全部原始点/片段并保存摘要后，Journey 才能进入 completed；清理失败必须留在可重试状态。
- 预计交通费用只能作为草稿建议，不能自动写入正式交易。

### 本地数据控制

- P0 导出固定为版本化 UTF-8 JSON；金额使用整数最小货币单位与币种，时间使用 ISO 8601，稳定 ID 只用于解释分录和正式关系。导出在一致性快照上生成，通过系统分享面板交付，分享完成、取消或失败后清理 App 临时副本。
- P0 始终只生成一个完整 JSON，不因低存储自动拆分、删字段或改成多文件。若系统报告容量不足，App 必须删除已经写出的部分文件和整次随机临时目录、保持源数据库不变、不打开分享面板，并明确提示“存储空间不足，请清理后重试；源数据没有改变”；同一用户随后可直接重试导出。
- 清理日历缓存不会删除系统日历事件，也不会删除用户已经确认的计划、提醒、Journey 或账务；它只移除本地来源快照和事件关系，并停止后续自动扫描。
- 删除已完成或已丢弃 Journey 会删除该 Journey 及其消费关系，但保留 TripPlan、正式交易和分录；未收口 Journey 必须先完成或丢弃。
- 删除本机全部数据前必须二次确认并停止定位与本地出发提醒；成功后创建全新的空本地资料，首笔账务仍需重新确认本币。数据库删除失败时整体回滚，不能显示完成。
- 系统权限不能由 App 代替用户撤回；数据清理完成后仍应如实展示当前系统授权状态，并说明可在系统设置中撤回。
- App 离开前台时必须用无业务正文的界面遮挡系统任务切换快照，返回前台后恢复原页面；P0 不因此新增隐私锁或解锁流程。
- 上次分享异常遗留的导出临时目录必须在下次启动时清除，并在再次导出前复查；若清除失败，禁止生成新导出并明确提示失败，不能静默累积副本。
- P0 候选发布包必须包含与实际行为一致的 App 隐私清单：不追踪、不配置追踪域、不把纯本地处理声明为离机收集，并如实列出 App 自有源码使用的 Required Reason API。自动化必须递归清点并验证 App bundle 内全部 App 与依赖清单，依赖声明变化必须阻断发布；签名候选 Archive 仍须通过 Xcode Organizer 生成聚合隐私报告并人工复核。以后新增网络、分析或同步前先更新清单和用户说明。
- P0 不提供生产日志、分析、崩溃上报、追踪或诊断包导出；生产 App 发生错误时只展示脱敏、可恢复的用户状态，不把金额、商户、日历标题、地点、坐标、轨迹或 OCR 原文写入控制台。候选发布必须通过生产 Swift 源码入口扫描，并以注入合成敏感日志的独立负向夹具证明校验器会阻断；未来启用任何生产诊断前必须先批准独立数据流并更新隐私声明。
- P0 的“诊断与关于”只是只读信息面：必须显示 App 名称、发布版本、构建号、“单设备本地”和“诊断收集未启用”。版本或构建号缺失时显示安全的“未知”状态，不崩溃也不伪造值。该信息面不读取或打包账务、日历、位置、设备标识或系统日志，不创建诊断文件、不写剪贴板、不发网络请求。
- P0 数据库目录、SQLite 主文件、WAL 与 SHM 必须实际使用 `completeUntilFirstUserAuthentication`；每次启动都修复既有目录和文件属性，不能只依赖首次创建。结构化导出的随机子目录和 JSON 必须实际使用 `complete`。由于 Simulator 不可靠返回 Data Protection 属性，自动化使用委托真实文件系统的记录器证明生产路径逐个发出正确保护操作；最低 iOS 18 真机再检查实际属性，并证明首次解锁后的锁屏行程可继续写入、锁屏时完整保护导出不可读且解锁后恢复。

### 语言与本地化

- P0 首发语言固定为简体中文 `zh-Hans`。英文及其他语言、应用内语言切换和未经过翻译验收的占位译文不在 P0 范围。
- 所有生产 SwiftUI 用户可见文案必须进入统一的 `Localizable.xcstrings`；App 显示名、Bundle 名称和日历、相机、定位等系统权限用途说明必须进入统一的 `InfoPlist.xcstrings`。不得存在第二份同类目录或手写 `.strings` 造成事实源分叉。
- 系统权限用途说明必须准确描述 P0 的本地用途和真实授权范围，不能暗示只读日历、全天后台定位、云同步、票据保存或其他未实现能力。
- 文案中的金额、日期、时间、距离、数量与动态名称必须保留类型正确的格式参数，并按用户地区生成值；不能依赖字符串拼接固定中文语序。
- 缺少翻译时必须安全回退到已审核的简体中文源文案。空键、空白结果、内部枚举、技术错误或未审核英文不得出现在生产用户路径。
- 每次新增或修改生产文案都必须同步更新字符串目录，并通过 Xcode 编译器提取结果与目录逐键一致、目录可编译、发布 App 实际包含简体中文资源的自动校验。

### 今天与显式关联

- “今天”不保存第二份事件、计划、Journey 或账务事实；它必须从各领域当前已保存数据组合展示，刷新不得改写原数据。
- 今日事件按设备当前时区的自然日和事件交叉判断；全天事件使用来源本地日期，不能因 UTC 转换漂移到前后一天。
- 下一次出发只从未取消的 `planned` 计划选择；地图路线过期可提示，但首页不在后台自动重算或覆盖用户确认的出发时间。
- P0 待处理数量只包含实际持久化且有处理入口的日历来源变化和未收口 Journey；不为 OCR、文件导入或同步冲突显示空占位。
- 行程—交易关联只能由用户确认，引用稳定 canonical root；同一交易 root 与 Journey 只有一条正式关系。解除关系不删除两端，也不修改账务分类或分录。
- 已收尾 Journey 的消费复盘必须持久化为“待复盘 / 本次无消费 / 已有关联消费”之一；空关系只表示待复盘，不能自动视为无消费。用户只能在不存在关联交易时明确选择“本次无消费”，之后仍可补记或关联真实交易；最后一条关系解除后重新回到待复盘。
- 标记无消费、创建关系、解除关系及复盘状态变化必须分别在同一 SQLite 事务中完成。已有 Journey 若已有正式关系则为已有关联消费，否则默认待复盘；不能用历史空关系代替用户确认。

### 离线、同步和删除

- 本地写入成功即视为用户操作成功；同步状态单独展示，不用网络错误否定本地结果。
- P0 本地数据库更新必须按已执行 migration 继续前向演进；同名 migration 的源代码变化不能被当作升级机制。空库安装与至少一个历史数据库升级夹具都必须通过，失败时保留原数据库并阻止进入可能产生部分写入的界面。
- 每次可同步变更携带全局唯一 mutation ID、实体版本和设备信息；服务端必须幂等。
- 账务和用户编辑过的出行冲突不使用静默 last-write-wins。
- 删除通过 tombstone 同步；用户执行完整删除时必须覆盖主数据、派生数据和待处理队列。

## 成功指标

指标采集必须先通过隐私评审；未接入分析平台时可用脱敏、本地聚合和可选用户研究验证。

| 目标 | 建议指标 |
| --- | --- |
| 快速记账 | 常见手动交易从点击新增到保存的中位时间不超过 15 秒；保存成功率不低于 99.5%。 |
| 日历转出行 | 已授权且包含有效地点的事件中，成功创建出行计划的比例；地点确认失败率。 |
| 提醒可信 | 普通本地提醒的调度成功率、权限拒绝可见率、过期路线被重新确认的比例。 |
| 行程闭环 | 已完成行程中有关联消费或明确选择“无消费”的比例。 |
| 数据质量 | OCR 草稿确认率、重复导入拦截率、账务不平衡错误为零。 |
| 稳定性 | 核心流程崩溃率、数据库写入失败率、活跃行程意外中断恢复率。 |

## 依赖与风险

- EventKit 读取需要 Full Access，授权文案和无授权路径会直接影响启用率。
- MapKit 路线不可用时必须允许手动设置出发时间并复制地址；当前版本不设置城市、交通方式或覆盖率发布门槛。
- 后台定位受系统调度、权限和耗电影响，必须用真机和真实移动场景验收。
- 端侧中文票据 OCR 的字段准确率未知，必须建立脱敏样本集；手动输入始终保留。
- 单一 `schema.sql` 适合 P0 声明式结构，首次处理复杂生产数据演进前必须重新评估迁移策略。
- P1 引入账号与同步前，需要同时解决中国大陆云资源、隐私政策、账号删除、RPO/RTO 和运营主体问题。

## 已关闭的范围决策

以下项目不再作为当前版本的未决问题，也不进入 P0/P1 实施计划：

1. 不设置 Apple 地图城市或交通方式覆盖门槛，不接入高德、百度、腾讯等国内路线或导航适配器；路线失败走手动降级。
2. 不长期保留原始轨迹；用户确认行程摘要后立即删除原始点，异常恢复只保留到行程完成或丢弃。
3. 不实现预算、结转、多币种预算或共享预算；保留单币种账户、分类统计和基础月度收支报表。
4. 不保存票据原图，不提供票据附件或云备份；OCR 图片仅在识别会话内临时存在。
5. 不启用 Time Sensitive 或 Critical Alerts；出发提醒只使用普通本地通知。
6. 不实现付费、订阅、免费容量、权益分层或购买入口；若未来需要商业化，必须新建独立 PRD，不从当前范围推导。

## 发布门槛

- 记账、日历到出行、实际行程和消费关联四条主路径均有可执行验收。
- 拒绝日历、通知、定位、相机或网络访问时均存在清晰的手动或只读降级路径。
- 不存在读取第三方支付流水或导航历史的误导文案。
- 数据导出、删除和权限撤回通过；P0 生产源码零日志/诊断入口扫描及合成负向夹具通过，未来获批观测能力另行进行敏感字段检查。
- App 与全部嵌入依赖的隐私清单随发布包打包、逐份结构有效且与 P0 零追踪/零离机收集行为一致；递归清单盘点通过，Xcode Organizer 聚合隐私报告完成复核。
- 发布包必须只包含一套 `zh-Hans` 生产本地化事实源：编译器提取的界面字符串与 `Localizable.xcstrings` 逐键一致，App 名称及全部系统权限用途说明与 `InfoPlist.xcstrings` 一致，两份目录均可编译且实际进入 App bundle；空键、缺失键、陈旧键和重复 `.strings`/字符串目录都阻断发布。
- XCUITest 必须能从真实 App 启动访问固定五 Tab 与“我的”本地数据说明，并看到发布版本/构建号、“单设备本地”和“诊断收集未启用”；清理日历缓存和删除本机全部数据都先展示准确范围且可取消。自动化不得为通过测试而真正删除测试机资料。
- iOS 26 长列表采用系统 Tab Bar 向下滚动最小化行为，密集滚动容器使用 hard scroll edge，在系统 bar 与正文之间保持明确高对比边界。
- iOS 26 Tab Bar 因向下阅读而收起后，点击已折叠的当前 Tab 胶囊必须恢复五个一级入口；最大辅助字号下也必须能从“我的”底部返回“今天”。
- “今天”和“账本”的账目搜索入口必须位于导航栏抽屉，不得遮挡列表末端内容；默认字号与最大辅助字号下，最后一条可见内容、搜索入口和取消操作都必须可达。
- Xcode 原生无障碍审计必须覆盖五个一级页面和快速记账页；描述、特征、点击区域、对比度和元素检测零问题通过，应用自有正文不得裁切。Dynamic Type 使用最大辅助字号深色外观可达性测试作为主证据；仅可按设计文档中的确定规则过滤 Xcode 26 `.dynamicType` 和精确匹配系统搜索框的 `.textClipped`；保留原始问题日志与过滤计数。P0 生产源码必须通过“无自定义动画入口”扫描及合成 `withAnimation` 负向夹具，证明系统 Reduce Motion 没有被应用自有动画绕过；VoiceOver 读取顺序与开启“减少动态效果”后的核心旅程最终仍以最低 iOS 18 真机录屏为发布证据。
