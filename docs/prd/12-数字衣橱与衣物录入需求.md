## 背景与问题

传统数字衣橱往往要求用户在首次使用时完整拍摄和标注大量衣物，录入成本高，价值出现得晚。另一方面，只依赖图片自动识别会把不确定属性写成事实，导致后续推荐使用错误信息。

产品需要让用户从今天正在穿的一套衣服开始，逐件、渐进地建立衣橱；照片和自动建议用于降低成本，但不能成为保存门槛。现实中的待洗、借出、已打包和归档状态必须可靠影响新推荐，同时不能改写历史穿搭。

## 目标用户

- 拥有一定数量衣物，但不愿一次整理完整衣柜的用户。
- 希望从一套 OOTD 或少量常穿单品开始获得价值的用户。
- 愿意拍摄衣物、选择已有商品图，或更偏好纯手工无图录入的用户。
- 经常遇到衣物待洗、借出、打包或换季归档，需要推荐反映现实状态的用户。
- 需要离线浏览和维护个人衣橱的用户。

## 产品目标

1. 用户可以从一件衣物或一套 OOTD 开始建库，不设完整衣橱数量门槛。
2. 用户从进入首次建档动作起，通过手工或一张本人 OOTD 照，在两分钟内确认至少两件衣物并保存可穿搭组合草稿；该草稿不自动成为穿搭计划或实际穿着。
3. 每件衣物具有稳定身份、用户确认的最小属性和明确的当前可用状态。
4. 图片与属性建议显著降低录入成本，但删除图片、识别失败或设备离线不影响结构化衣物存在。
5. 待洗、借出、已打包和归档等现实状态及时影响新推荐，历史搭配仍保留当时事实。
6. 衣物照片与人物照片、生成结果分开处理，用户可只移除照片而保留衣物和历史。

## 非目标

- 不强制首次录满指定数量衣物，不以“衣橱完整度”阻止手工搭配或穿搭记录。
- 不从完整照片库、社交媒体、购物平台、账单、通知或订单中静默抓取衣物。
- 不把模型猜测的尺码、材料、保暖、洗护、价格或品牌当作事实。
- 不建立共享或家庭衣橱、租赁、二手交易、库存估值、购物清单或商品导购。
- 不提供品牌目录、商品搜索、社区内容流、联盟链接或未拥有商品推荐。
- 不要求每件衣物必须有照片，不因图片质量不足阻断今日穿搭决定。
- 不在录入流程中实现云端试穿、动态预览或远程推荐排序。
- 首发不提供衣物图片、组合草稿或生成媒体的下载、导出、社交分享和公开链接。

## 功能范围

### 首发必备能力

- 从“今日”和“衣橱”入口新增衣物，两处写入同一个人衣橱并遵循相同确认规则。
- 支持无图手工新增，以及下表三种彼此不混用安全规则的图片输入模式。
- 允许先填写名称、类别和当前状态，其他属性未知时仍可保存并稍后补全。
- 对类别、颜色、图案、季节、正式度、保暖和材质提供可修正建议；建议、用户确认和未知状态必须清楚区分。
- 提供默认“可穿”视图，以及按类别、状态和已确认属性浏览或筛选。
- 支持可穿、待洗、借出、已打包与归档；状态变化影响新推荐，不静默改写已保存方案。
- 对疑似重复衣物提供并排确认，用户可合并、分别保留或取消；不得自动删除或合并。
- 支持批量整理的逐件确认、中断说明和继续处理；单项失败不撤销已确认的其他衣物。
- 用户可以移除衣物照片但保留名称、属性、状态和历史引用。
- 所有基础录入、编辑、浏览、状态维护和草稿处理在无网络时可用。

### 三种图片输入模式

| 模式 | 允许输入 | 处理与结果 |
| --- | --- | --- |
| 本人 OOTD | 用户主动选择、确认本人且年满 18 周岁、画面只有一个主要人物的当日穿搭照片。 | 继承 PRD 11 的选图前说明、本人/18+ 声明、多人阻断、安全解码、元数据净化和临时生命周期；只产生待确认衣物草稿与组合草稿。 |
| 单件衣物 | 平铺、悬挂或用户拍摄的一件主要衣物；一双鞋可作为一个单品。 | 明显人物或无法分离的多件重叠进入换图、手工选主体或无图路径；不自动转入人物照片流程。 |
| 商品图或购物截图 | 用户主动选择、确认有权使用且衣物确实属于本人衣橱的图片。 | 在本机先裁掉人物、价格、订单、地址和页面无关内容；不能安全去除可识别人物或敏感正文时，不保存原截图，改用换图或无图录入。 |

同一张本人 OOTD 若还要用于数字形象，必须分别展示“衣物拆分”和“人物参考”两个目的并让用户逐项选择。只选择衣物拆分时，完成草稿确认、取消、失败或批准的临时期限到期后，应清理人物源图和人体派生内容，不得创建可复用人物形象。

### 后续或条件能力

- 更丰富的批量拍摄、补拍背面、细节或洗护标。
- 获批的本地辅助识别、相似度建议和更精细的前景处理。
- 多设备结构化衣橱同步，以及经过独立同意的衣物图片同步。
- 由用户逐件确认的购买记录关联。
- 衣物图片作为静态 AI 试穿输入；必须满足单独的质量、同意和云端门禁。

条件能力关闭时，手工、无图与离线路径必须保持完整，不能展示无法完成的入口。

## 核心用户故事

- 作为新用户，我可以先添加今天身上的几件衣物，而不是整理整个衣柜。
- 作为不愿拍照的用户，我可以用名称、类别和状态创建无图衣物并参加基础推荐。
- 作为用户，我可以从一张 OOTD 照确认多件草稿，并明确知道遮挡或未知的属性。
- 作为用户，我知道这次导入只创建衣物草稿和组合草稿；我主动保存后才形成计划，主动确认日期和“实际穿了”后才形成实际穿着。
- 作为用户，我可以连续拍摄或选择多件衣物，逐件确认后随时退出并继续。
- 作为用户，我可以修正系统建议，后续重新识别不会覆盖我的确认值。
- 作为拥有多件相同基础款的用户，我可以将疑似重复项保留为不同衣物。
- 作为用户，我可以把衣物标记待洗、借出、已打包或归档，让新推荐符合现实。
- 作为用户，我可以只删除照片，不丢失衣物事实、穿着历史和反馈。
- 作为离线用户，我可以浏览、筛选、新增和修改状态，稍后联网不会覆盖本地确认。
- 作为使用辅助技术的用户，我可以通过文字而非仅靠图片、颜色或透明度识别衣物和状态。

## 业务规则

| 需求 ID | 规则 |
| --- | --- |
| `WARDROBE-REQ-001` | 衣物必须有稳定业务身份，不以文件名、图片摘要、照片库标识或本地顺序作为跨端身份。 |
| `WARDROBE-REQ-002` | 名称、类别和当前状态是最小保存信息；图片、品牌、价格、材质和尺码不是必填项。 |
| `WARDROBE-REQ-003` | 自动识别结果默认为建议；用户确认或修正的值优先，模型更新不得静默覆盖。 |
| `WARDROBE-REQ-004` | 不确定属性保持未知；不得以默认值补齐后作为硬过滤事实。 |
| `WARDROBE-REQ-005` | 归档衣物不进入新推荐；待洗和借出默认不可用；已打包只在用户明确匹配的上下文中可用。 |
| `WARDROBE-REQ-006` | 衣物当前状态与历史搭配快照分离；改名、归档或移除照片不重写历史。 |
| `WARDROBE-REQ-007` | OOTD 中被遮挡的衣物必须标记信息不完整，不能生成隐藏细节并将其当作真实衣物事实。 |
| `WARDROBE-REQ-008` | 疑似重复只提示；在用户明确确认前，不自动合并、覆盖或删除任何一件。 |
| `WARDROBE-REQ-009` | 衣物图片可以缺失；图片丢失、删除或处理失败不得删除衣物及其历史引用。 |
| `WARDROBE-REQ-010` | 移除照片必须覆盖由该照片直接产生的展示与视觉派生内容，并处理仍在引用它的条件任务。 |
| `WARDROBE-REQ-011` | 保存的未来方案遇到衣物状态变化时显示冲突，不静默替换其中的衣物。 |
| `WARDROBE-REQ-012` | 基础衣橱不因推荐、浏览或状态维护自动上传图片、属性或用户标签。 |
| `WARDROBE-REQ-013` | 商品图导入必须由用户主动选择并确认拥有该衣物；价格、订单、地址和页面文案不得自动成为衣物事实。 |
| `WARDROBE-REQ-014` | 每个批量项目独立确认；失败或退出不回滚已经确认的衣物，也不能重复创建它们。 |
| `WARDROBE-REQ-015` | 本人 OOTD、单件衣物、商品图使用三套明确输入规则；一种模式的允许内容不能静默扩展到另一种。 |
| `WARDROBE-REQ-016` | 本人 OOTD 继承 `AVATAR-REQ-002`、`AVATAR-REQ-005`、`AVATAR-REQ-006` 与 `AVATAR-REQ-013`：本地无照片核心不要求年龄声明，选图前确认本人且 18+，多人阻断并先完成净化。 |
| `WARDROBE-REQ-017` | OOTD 导入默认只产生待确认衣物草稿和组合草稿；用户主动保存才创建 `OutfitPlan`，主动确认日期和“实际穿了”才创建 `WearEvent`。 |
| `WARDROBE-REQ-018` | 同一 OOTD 的衣物拆分与人物参考是独立目的；未选择人物参考时不得保留可复用人物源图、人体派生物或数字形象。 |
| `WARDROBE-REQ-019` | 商品图或购物截图在本机移除可识别人物、价格、订单、地址和无关页面内容后才能成为衣物图片；无法安全净化时不保存原图。 |
| `WARDROBE-REQ-020` | 首次价值完成要求两分钟内至少两件衣物确认成功且一份包含这些衣物的可穿搭组合草稿原子保存成功；未确认草稿、半保存和自动识别完成均不计入。 |
| `WARDROBE-REQ-021` | 首发不提供衣物、组合或生成媒体下载、导出、社交分享和公开链接。 |

## 用户可见状态与失败恢复

| 状态或失败 | 用户看到 | 恢复路径 |
| --- | --- | --- |
| 空衣橱 | 从一件开始的说明，不展示完成度压力 | 无图新增、拍摄、选择图片或从 OOTD 开始。 |
| 待确认草稿 | 建议、未知字段、来源和剩余数量 | 修正后保存、跳过、继续或全部丢弃未确认草稿。 |
| 图片模糊或裁切 | 一个主要问题和对推荐/视觉的影响 | 重拍、换图或保存为无图衣物。 |
| 单件衣物模式包含人物或多件重叠 | 当前无法安全形成单件素材 | 重新拍摄、手工选择主体或无图新增；不自动保存人物图，也不静默切换模式。 |
| 本人 OOTD 包含多人或声明未完成 | 当前 OOTD 不进入拆分，临时输入不保留 | 选择只有本人的照片、完成本人且 18+ 声明，或改用无图/单件衣物路径。 |
| 商品图仍含可识别人物、订单或地址 | 当前图片不能安全保存为衣物素材 | 在本机重新裁剪、换图或无图新增。 |
| 属性建议不可用 | 名称、类别和状态仍可编辑 | 手工确认最小信息并保存。 |
| 疑似重复 | 两件的已知属性、图片和状态差异 | 合并、分别保留或取消本次新增。 |
| 批量处理中断 | 已保存数量、待确认数量和本机草稿说明 | 继续、逐件处理或丢弃剩余草稿。 |
| 存储不足 | 当前项目尚未确认，已保存项目不受影响 | 清理空间后重试，或无图保存。 |
| 图片损坏或丢失 | 无图占位与结构化信息 | 重拍、换图或继续无图使用。 |
| 离线 | 明确显示本地状态，不等待网络 | 完成基础新增、编辑和状态维护；联网后仍以用户确认值为准。 |
| 状态与未来方案冲突 | 受影响方案和单品状态 | 替换、恢复状态或保留为仅计划。 |
| 照片删除中/失败 | 图片立即隐藏并说明仍在清理 | 重试清理；衣物和历史始终可用。 |

## 成功指标及防误导指标

### 成功指标

- 新用户从进入手工新增或本人 OOTD 导入起，两分钟内确认至少两件衣物并原子保存组合草稿的比例；未确认草稿和自动识别完成不计入。
- 单件衣物从进入新增到确认完成的中位时间。
- 无图新增、单件图片、OOTD 拆分和批量整理各自的完成率。
- 每件衣物平均需要用户修正的字段数与后续纠错率。
- 空衣橱用户在首次会话内获得完整可穿路径的比例。
- 待洗、借出、打包和归档状态被正确维护并影响推荐的比例。
- 批量中断后成功继续的比例，以及重复创建率。
- 无照片和离线用户完成新增、编辑与状态维护的比例。
- 图片移除后衣物与历史完整保留的成功率。

### 防误导与护栏指标

- 不把系统自动生成但未经用户确认的草稿计为已录入衣物。
- 不通过预填未知属性、默认接受建议或隐藏跳过入口缩短录入时长。
- 不把图片处理成功率等同于衣物事实准确率；需单独跟踪用户修正和未知比例。
- 不以衣橱项目数量作为核心成功指标，避免推动重复项或低质量批量导入。
- 无图衣物的保存、状态维护和基础推荐资格不得被人为降低。
- 疑似重复提示的误合并率和撤销/恢复请求必须作为质量护栏。
- 图片删除只有在承诺的直接派生内容完成清理后才计为成功。

## 依赖与风险

- 冷启动价值依赖“今日”流程能在新增后恢复原场景和已锁定单品。
- OOTD 拆分可能受遮挡、叠穿和拍摄角度影响，易把推测细节误当事实。
- 相似基础款可能被误判重复，自动合并会污染状态和穿着次数。
- 类别、颜色、保暖和正式度建议存在偏差，需要未知态和低成本修正。
- 批量流程、低存储或异常退出可能产生未确认草稿或图片残留。
- 衣物状态维护过重会降低使用率，需要支持在详情、今日方案与穿后反馈中快速修改。
- 衣物图片仍可能包含人物、住址、订单等无关内容，需要最小化和明确恢复路径。
- 后续同步和云端试穿会扩大图片生命周期，必须独立评审，不能复用基础录入同意。

## 发布门禁

- 无照片、无网络且不授予相机或完整图库权限时，能够新增、编辑、浏览、筛选和修改状态。
- OOTD-first、单件新增和批量整理使用一致的衣物语义，新增后能返回原决策上下文。
- 用户确认值、模型建议和未知属性在 UI 与业务行为上可区分，重新处理不会覆盖用户修正。
- 待洗、借出、打包和归档状态有可执行的推荐过滤与历史保留证据。
- 疑似重复不会自动合并；批量中断、低存储和重启不会重复创建或留下半完成衣物。
- 图片移除、衣物删除与历史保留的影响说明清楚，异常清理可重试且不误删其他衣物。
- 人物、GPS、订单和原文件名等无关信息不会因基础衣橱录入进入网络、日志或默认导出。
- 最大辅助字号、VoiceOver、深色模式和仅文字/无图状态通过核心流程验收。
- 条件云能力未通过供应商、同意、隐私和删除门槛时，基础衣橱无远程依赖且不存在不可用入口。
