## 必须分开的业务事实

| 对象 | 含义 | 是否私人 | 不能推导出的事实 |
| --- | --- | --- | --- |
| Look | 内置/虚拟人物的造型配方 | 用户保存时私人 | 不表示拥有这些衣物，也不表示实际穿着 |
| OutfitPlan | 某日打算穿什么 | 是 | 不表示已经穿过 |
| WearEvent | 主动确认的实际穿着，可一日多次 | 是 | 不自动发表日记或社区内容 |
| WearFeedback | 对实际穿着的独立可撤回反馈 | 是 | 不等于对社区作者或帖子评价 |
| DiaryEntry | 某日的文字、照片、心情、场合 | 始终私人 | 不因关联计划/Look 自动创建实际记录 |
| Post + PostRevision | 明确公开的图文笔记与被审核版本 | 草稿私人；批准版本公开 | 不把日记整行、衣橱 ID 或私有媒体直接公开 |

日记可选关联一个实际事件、一个计划、一个保存 Look；可以都不关联。每条记录只表达一次记录，数据库不设 `(owner_id, local_date)` 唯一约束。日历按原始本地日期聚合；跨时区不重写过去记录。统计“穿了几天”来自实际事件，不数日记/点赞/保存次数。

## 推荐的首版行为合同

19-03 已固定日记标题 80 字、正文 5,000 字、心情/场合各 40 字和最多 9 张图。19-04 已固定帖子标题 80 字、正文 3,000 字、最多 9 图、最多 5 个 1～20 字规范化标签；日记图与社区发布图均为 12 MiB/24 MP 内单帧 JPEG，但用途隔离。空字符串规范为空值，正文或图片至少一项。19-05 已固定评论正文 1～500 字，只允许根评论和一级回复，提交后先审核且不可编辑。

- 日记：创建、编辑、删除、日期/文字筛选、月日历；可以补记过去日期，未来安排使用计划。心情/场合是可选短标签，不推断健康或位置；第一版不做习惯打卡、运动、账本。
- 发帖：可以独立写，也可从日记/Look/实际记录导入选定字段。默认只导入用户选中的公开文字/图片/造型摘要，不导入心情、精确日期、原时区、私人衣物 ID、私人备注或定位。作者预览并明确提交。
- 首版社区允许净化后的普通穿搭图片、已发布内置 Look 渲染图；本人采集原图禁止作为公开媒体。AI 生成结果需对应生成/分享门禁通过后启用，图片附来源标签，不把未来支持写成当前可发。
- 发现流按发布时间倒序；关注流按关注作者已发布内容倒序。先不做机器学习推荐、粉丝写扩散、热度分和独立搜索集群。标签和有限关键字搜索由 PostgreSQL 有界查询承载。
- 点赞/收藏/关注为幂等关系；收藏列表只本人可读。允许取消，不允许自关注。评论只做根评论与一级回复，不建设无限嵌套楼层；评论提交后先审核再可见。
- 通知首版为站内列表：评论、回复、关注、审核结果。赞藏只计数；收藏者身份不向作者发通知。短视频、直播、私信、购物、广告和复杂推荐分期。
- 所有人物照片的既有来源/用途限制保持；图文社区不能借普通媒体入口绕过人物采集和 AI 处理约束。账号准入年龄、运营地域和具体审核政策需发布前另定，不在本轮虚构合法合规结论。

## 发布、审核与撤回

`草稿 → 提交审核 → 通过并发布 / 拒绝后编辑重提`。发布后的编辑创建新 revision；新版本审核期间继续展示原批准版本。作者撤回后所有公开读取立即拒绝，回到私人草稿；再次发布必须重新审核。

`posts.state` 控制整体状态（draft/pending/published/withdrawn/removed/deleted），`post_revisions.review_state` 控制版本（draft/pending/approved/rejected/cancelled）。审批必须同时比较 post revision、目标 revision、审核轮次和期望状态；迟到任务不得恢复已撤回/下架内容。下架仅运营可解除且须明确重新审核；作者无法自助 publish 绕过。

首版用人工审核 API 闭环；不假设已接入自动审核供应商。自动媒体净化不是内容审核。没有审核能力或审核失败时保持 pending，不公开。管理员角色为固定 `user/moderator/admin`，无自助提权入口，无首个注册用户自动变管理员。账号封禁撤销会话并隐藏内容。

公开资料只有公开名称、简介、头像和公开帖子/计数。邮箱、凭据、用途同意、日记、实际事件、衣物列表和私有资产标识不得出现在公开 DTO。公开内容可以被匿名看到；屏蔽控制已登录双方的互动和个性化列表，不承诺能阻止对方退出登录后浏览公开内容。

## 存储与中间件责任

继续使用一个 Go 模块/模块化单体、Gin/Huma/GORM，不增加新框架或服务。一个 PostgreSQL 业务库按表分域；开发、测试、生产使用独立库和凭据。MinIO 保存二进制；Redis 只做限流与可丢失缓存；RabbitMQ 承载媒体处理、删除与通知投递。PG 是所有状态与关系的事实源。

点赞、关注、评论创建和审核决定同步事务提交；耗时衍生图、通知通过同事务 Outbox 异步执行。RabbitMQ 至少一次投递，消费者利用 Inbox 与唯一业务键去重；不宣称端到端恰好一次。队列中只传 ID/revision/目的，不传日记正文或照片字节。队列故障不把数据库已保存内容变成“没保存”；公开发布必须等必须的媒体和审核条件满足。

MinIO 分离私有源文件和社区衍生图的桶/前缀与服务凭据；社区桶也不允许匿名 list/read。图片通过检查当前 post 状态的 HTTP 媒体入口读取，首版不缓存可撤回内容到公共 CDN，也不发可绕过撤回的长期签名 URL。撤回保证后续受控读取拒绝；已下载副本无法追回，应在发布说明明确。

## 删除与故障的跨领域设计

- 删除日记默认保留已独立发布的笔记，提示影响并允许选择同时撤回相关笔记；来源引用置空，笔记不自动改文案。
- 删除实际穿着清除关联反馈、日记来源关联和统计证据，保留独立日记文字；删除衣物仍沿用历史清除/连同计划删除合同，公开内容需单独展示影响。
- 删除媒体前查询所有引用；仍被笔记使用时先撤回受影响笔记。禁止删除共享对象后让另一条内容静默破图；发布使用独立衍生副本。
- 删除账号先事务标记 deleting、撤销会话、关闭全部公开可见性、创建媒体删除任务，再异步清理对象版本；删除确认后才清理身份关联。现有账号级联删除会移除媒体/删除任务元数据，须先改为可追踪流程，不能在级联后才找对象。
- 审核/举报审计只保留必要的动作、原因码、匿名化引用，不长期存放被删正文和原图；保留期限在上线前固定到配置和验收，不用“永久软删除”代替删除。
