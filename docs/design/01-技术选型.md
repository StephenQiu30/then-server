# 技术选型基线

## 状态

已确认，2026-08-09。

本文是“于是”项目的技术选型事实源。未在“待业务决策”中列出的技术不得在实现时自行替换；版本升级、架构替换或新增同类框架必须通过独立设计决策说明影响、迁移和回滚方式。

## 选型目标

- 只开发 iOS，最大化利用 Apple 原生能力，不维护跨平台抽象成本。
- 记账、日历缓存和行程结束在断网时可用，联网后可靠增量同步。
- 后端保持一个 Go module、一个进程和一个部署单元。
- OpenAPI、服务端数据库结构和客户端本地数据库都只有明确的事实源。
- 对金额、日历和精确位置执行最小采集、可撤回、可删除和中国内地数据驻留原则。
- 首版避免为尚不存在的规模引入微服务、消息队列、Kubernetes 或多套数据框架。

## iOS 客户端

### 平台与架构

- 使用 SwiftUI + Observation；UIKit 只桥接缺少 SwiftUI 接口的系统控制器。
- P0 保持一个 `ThenApp` Swift module 加测试 target；Feature 先按目录和协议隔离，不拆成内部 framework 或 Swift Package。
- 使用 feature-first + MVVM + Repository。ViewModel 使用 `@Observable`，View 和 ViewModel 不直接接触 GRDB、OpenAPI 生成类型或系统 framework 的可变对象。
- 使用 Swift Concurrency 和结构化并发，不引入 RxSwift、ReactiveSwift 或以 Combine 作为全局状态框架。
- App target 设置 Swift 6 language mode、Complete Strict Concurrency、Approachable Concurrency 和 Main Actor 默认隔离。Data 与 Domain 代码在同一 module 内通过 `nonisolated`、值类型、`Sendable` 和专用 actor 显式脱离 UI 隔离。
- 依赖使用初始化器或显式环境容器注入，不引入第三方 DI 容器。
- 依赖管理只使用 Swift Package Manager，不引入 CocoaPods 或 Carthage。
- 格式化使用 Xcode 工具链自带的 `swift format`；当前随工具链版本为 `6.3.0`。

最低 iOS 18 仍覆盖 iPhone XS、XR、SE 2 及更新机型，同时允许统一采用现代 Observation、Vision 和 Core Location 接口，避免为了尚未验证的少量旧系统用户维护两套位置和 OCR 实现。Xcode 工程不得擅自提升到 iOS 26，也不得在没有覆盖率数据和兼容成本评估时降低最低版本。

### 本地数据

选择 GRDB，不选择 SwiftData 或 Core Data：

- 使用一个 SQLite 数据库、`DatabasePool`、WAL 和 `DatabaseMigrator`。
- 账务 `transaction + posting`、离线 mutation/outbox、tombstone 和临时行程轨迹使用显式约束与事务。
- 高频定位点先在 Data 层批量可靠落盘；用户确认摘要或丢弃行程后原子删除，不进入 SyncService，页面生命周期不拥有轨迹写入任务。
- GRDB Record 和 SQL 只存在于 Data 层，必须转换为纯 Domain struct。
- 令牌和长期凭据存 Keychain；数据库文件使用 `completeUntilFirstUserAuthentication` Data Protection，使用户首次解锁后仍能在锁屏行程中可靠写入。P0 不引入 SQLCipher，除非后续威胁模型证明系统静态保护不足。
- 客户端 schema 迁移集中在一个明确的 `DatabaseMigrator` 注册文件中；不在多个 Feature 内隐式建表。

GRDB 提供显式 SQL、事务、WAL 并发和可审计迁移，适合双重记账、离线同步与高频轨迹。SwiftData 的持久化模型和隐式迁移容易渗入领域层；Core Data 对全新项目的对象图与 Context 成本没有相应收益。GRDB 的当前正式版本与能力见 [GRDB 7.11.1](https://github.com/groue/GRDB.swift/releases/tag/v7.11.1) 和 [GRDB 文档](https://github.com/groue/GRDB.swift)。

### 网络与 API

- `backend/openapi.yaml` 是唯一契约；Xcode Build Tool Plugin 在 DerivedData 中生成 types 和 client。
- 生成 Client 使用 `OpenAPIURLSession`，不再引入 Alamofire、Moya 或第二套手写网络 Client。
- 认证、追踪 ID、超时和安全重试通过 OpenAPI Client Middleware 与手写 Repository/Service 封装。
- 只有幂等请求或携带幂等键的写请求允许自动重试；认证刷新必须防止并发刷新风暴。
- 生成 transport DTO 必须在 Repository 边界映射为领域模型。

固定组合为 [Generator 1.13.0](https://github.com/apple/swift-openapi-generator/releases/tag/1.13.0)、[Runtime 1.12.0](https://github.com/apple/swift-openapi-runtime/releases/tag/1.12.0) 和 [URLSession Transport 1.3.1](https://github.com/apple/swift-openapi-urlsession/releases/tag/1.3.1)。

### 测试

- 纯领域与 ViewModel 测试使用 Swift Testing。
- 系统 framework 适配器通过协议 fake 测试；关键权限与后台行为必须真机验收。
- 核心用户旅程使用 XCUITest，不用快照测试替代行为验收。
- 数据库测试使用临时 SQLite 文件并实际执行全部 GRDB migrations、约束、事务和并发场景。

## Go 后端

### 运行形态

- 一个 `go.mod`、一个 `main.go`、一个进程、一个 OCI 镜像和一个部署单元。
- HTTP 服务、必要的定时任务和 Outbox 消费共享同一个根 `context.Context`、健康状态和优雅退出流程。
- 使用标准库 `net/http` + chi；不使用 Gin、Fiber、Echo 或完整 Web framework。
- 使用手写纯 Go request/response/domain struct。OpenAPI 不生成 Go server、DTO 或框架接口。
- 使用标准库 `encoding/json`、`errors`、`context`、`log/slog` 和 `net/http`；只有标准库明显不能满足已批准需求时才增加依赖。

chi 完全兼容 `net/http`，可以保持 transport 层轻量；pgx 直接暴露 PostgreSQL 事务、类型和连接池能力。固定版本为 [chi v5.3.1](https://github.com/go-chi/chi/releases/tag/v5.3.1) 与 [pgx v5.10.0](https://github.com/jackc/pgx/releases/tag/v5.10.0)。

### 数据访问与配置

- 使用 `pgxpool`，Repository 中编写参数化显式 SQL；不经 `database/sql` 适配层。
- 不使用 ORM、Active Record、sqlc 或会拆出查询定义文件的生成器。
- 配置使用 typed struct，通过 `os.LookupEnv`、`strconv` 和显式校验加载；不引入 Viper。
- 金额使用整数最小货币单位；多表账务写入和 Outbox 事件必须在同一 pgx transaction 中提交。
- `updated_at`、Outbox 和审计字段由 Repository 明确写入，不依赖隐式 trigger。

### 日志与可观测性

- 应用日志使用 `log/slog` JSON 写入 stdout/stderr，包含 request ID、稳定错误码和耗时。
- tracing 与 metrics 使用 OpenTelemetry，通过 OTLP/HTTP 输出；HTTP instrumentation 使用 `otelhttp`。
- OpenTelemetry Go logs 当前不作为基线，日志仍由 slog 交给部署平台采集。
- 不记录 SQL 参数、访问令牌、金额明细、日历标题、精确地址、轨迹点或 APNs payload 正文。
- 最低健康端点为进程存活与依赖就绪两类；就绪检查必须反映数据库不可用状态。

### 测试

- Service 使用 `testing`；HTTP 使用 `httptest`；不锁定 testify 或 mock framework。
- Repository、schema、事务、幂等和同步测试使用 Testcontainers for Go 启动真实 `postgres:18.4`。
- contract test 使用 [kin-openapi v0.146.0](https://github.com/getkin/kin-openapi/releases/tag/v0.146.0) 加载嵌入的 `backend/openapi.yaml`，校验路由、参数、请求、状态码和响应 schema；kin-openapi 不生成代码。
- kin-openapi 官方目标包含 OpenAPI 3.1，但业务 schema 落地前仍须用 nullable union、`const`、`$ref` sibling 和请求/响应校验做兼容 POC；未通过的 3.1 关键字不得进入契约。

## API 与 Swagger

- 契约固定为 [OpenAPI 3.1.2](https://spec.openapis.org/oas/v3.1.2.html)。暂不采用 OpenAPI 3.2，因为 Swift OpenAPI Generator 对 3.2 仍标记为 preliminary。
- `backend/openapi.yaml` 同时服务 iOS 生成、Go contract test 与 Swagger UI；不得出现第二份 YAML/JSON、Go 注解契约或 `api/` 目录。
- Spectral 检查风格和完整性，oasdiff 阻止未批准的破坏性变更，Swift 生成与编译验证客户端兼容性。
- Swagger UI 使用固定的 `swagger-ui-dist` 资产并嵌入 Go 二进制，运行时不加载公共 CDN；只读取嵌入的唯一契约。
- Swagger UI 仅在开发、测试环境开启。生产默认关闭；确需开启时增加鉴权、网络限制并禁用持久化授权。

Swagger UI `v5.32.12` 支持 OpenAPI 3.1 系列，版本见 [官方 release](https://github.com/swagger-api/swagger-ui/releases/tag/v5.32.12)。Apple 生成器的规范支持范围见 [Swift OpenAPI Generator](https://github.com/apple/swift-openapi-generator)。

## PostgreSQL schema 管理

`backend/schema.sql` 是期望数据库结构的唯一事实源，不创建 migrations 或 queries 目录，也不允许应用启动时自动修改数据库。

### 新数据库、本地和测试

对空数据库原子执行完整 schema：

```sh
psql -X --set=ON_ERROR_STOP=1 --single-transaction \
  --file=backend/schema.sql "$DATABASE_URL"
```

### 已有环境

Atlas Community 只负责从当前状态计算到 `backend/schema.sql` 的声明式差异。必须先 dry-run 并保存评审证据：

```sh
atlas schema apply \
  --url "$DATABASE_URL" \
  --to "file://backend/schema.sql" \
  --dev-url "docker://postgres/18/dev" \
  --schema public \
  --dry-run
```

每个环境使用专用数据库和最小权限部署身份，命令只管理 `public` schema；不得让 Atlas 管理共享数据库中的其他用户 schema。执行前必须确认备份或 PITR、数据转换、锁表影响、回滚和验收计划；任何 `DROP` 计划默认阻断，只有独立数据变更计划明确批准后才能继续。生产禁止 `--auto-approve`。人工确认后才运行去掉 `--dry-run` 的同一命令。[Atlas declarative apply](https://atlasgo.io/declarative/apply) 会展示实际变更并默认要求确认。

Atlas Community 的固定 P1 首版子集只包含 enum、table、column、constraint、index 与 comment。P1 首版不使用 extension、function、trigger、RLS 或 seed DML。若后续必须使用这些对象且继续坚持单一 desired-state 文件，应采购支持相应对象的 Atlas 版本；否则必须重新批准版本化迁移。第一次对持久生产数据执行回填、破坏性或大表变更前，也必须重新评估当前单文件策略。

## Apple 系统能力与外部集成

### 日历与提醒

- EventKit 读取系统日历；iOS 没有只读授权，只有用户开启同步时才申请 Full Access。
- 同步已进入系统日历数据库的事件，不承诺读取微信、钉钉等 App 的私有事件。
- EventKit identifier 不作为永久业务主键；保存来源指纹并处理事件移动、重复、删除和完整同步。
- 出发提醒使用 UserNotifications 本地通知。远程通知只用于同步变化提示，不作为唯一准点提醒。
- 通知级别固定为普通 `active`；不启用 Time Sensitive 或 Critical Alerts，也不保留隐藏开关。

Apple 的权限和变更模型见 [EventKit access](https://developer.apple.com/documentation/eventkit/accessing-the-event-store) 与 [EKEventStoreChangedNotification](https://developer.apple.com/documentation/eventkit/ekeventstorechangednotification)。

### 地图、导航和轨迹

- Core Location + MapKit 是 P0 基础能力；`MKDirections` 是路线 ETA 的默认实现。
- 定义 `RoutePlanningService`，结果包含 MapKit 来源、WGS-84 坐标、交通方式和有效期；不以城市或交通方式覆盖率作为发布门槛。
- 定义 `ExternalNavigationService`，只实现 Apple 地图交接；不接入高德、百度、腾讯 adapter 或导航 SDK。
- Apple 地图交接是单向的，不承诺读取导航历史、实际轨迹、偏航、到达状态或消费记录。
- 实际轨迹只在用户明确点击开始记录后由本 App 通过 Core Location 临时采集；使用 When In Use 与可见后台活动会话，不默认申请 Always，摘要确认或行程丢弃后删除原始点。
- 当前坐标统一使用 WGS-84，不实现 GCJ-02/BD-09 转换或供应商坐标边界。

Apple 地图调起使用 [`MKMapItem.openMaps`](https://developer.apple.com/documentation/mapkit/mkmapitem/openmaps%28with%3Alaunchoptions%3A%29)。实际后台定位遵循 [Core Location live updates](https://developer.apple.com/documentation/corelocation/adopting-live-updates-in-core-location)。

### OCR

- 使用 Vision/VisionKit 端侧识别，P0 不把账单或票据图片发送给云 OCR。
- 相机扫描、相册导入和手动输入都必须可用；设备不支持 Data Scanner 时自动降级。
- OCR 结果进入待确认箱；金额、日期、商户、币种和分类通过规则校验并由用户确认，不能直接成为已确认账务。
- 图片只在识别会话内临时存在，确认、取消或会话结束后删除；当前不保存票据原图、附件或云备份。

端侧能力参考 [Vision text recognition](https://developer.apple.com/documentation/vision/recognizing-text-in-images) 与 [VisionKit](https://developer.apple.com/documentation/visionkit)。

### 推送和部署

- P1 远程推送由 Go 后端使用 token-based authentication 直接连接 APNs，不引入极光、个推或 Firebase SDK；P0 出发提醒只依赖本地通知。
- APNs payload 只携带不透明 ID，不携带金额、标题、精确地址或轨迹。
- 当前不提供文件上传或对象存储；OpenAPI、PostgreSQL 与 iOS 模型均不预建附件或原始轨迹云备份结构。
- P1 后端以一个 OCI 镜像部署到中国内地地域，计算、托管 PostgreSQL 和 KMS 使用同一云、同地域与私网连接。
- P1 首版不使用 Kubernetes；托管容器或单实例/小规模编排即可。

APNs 连接采用 Apple 的 [token-based connection](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)。

## 明确不采用

- Flutter、React Native、纯 H5、低代码壳。
- SwiftData、Core Data、Realm、CloudKit 作为本地或跨设备同步事实源。
- Alamofire、Moya、RxSwift、第三方 DI 容器。
- Go 微服务、独立 API/Worker/Migrate 进程、Gin/Fiber/Echo、ORM、sqlc。
- GraphQL、gRPC 作为 App 的公开业务接口；P1 云接口使用 REST/JSON。
- Redis、Kafka、RabbitMQ、Kubernetes；没有证据前由 PostgreSQL 和单进程承担。
- 从 OpenAPI 生成 Go server/DTO，或手写/复制第二份 iOS API 模型。
- 自动读取微信/支付宝个人流水、Android 通知监听或爬取第三方导航私有数据。
- 第三方云 OCR、第三方推送 SDK、公共 Swagger CDN 作为 P0 依赖。
- 未经用户主动开始的全天候后台定位。
- 预算、票据附件、长期原始轨迹、国内地图 adapter、Time Sensitive、订阅、付费和容量权益系统。

## 待业务决策

下列项目没有足够的商业、资质或产品信息，当前不锁具体供应商。未决不阻塞本地优先 P0 开发：

| 决策 | 默认过渡方案 | 锁定前需要的信息 |
| --- | --- | --- |
| P1 账号与多设备同步范围 | P0 固定本地可用；接口预留认证边界但不实现伪入口 | P0 验证结果、注销/恢复策略、合规与云资源；P1 优先评估 Sign in with Apple |
| 中国内地云厂商 | 只锁 OCI/PostgreSQL/KMS 接口 | 运营主体、备案、成本、地域、RPO/RTO、合同和退出机制 |
| 产品分析与崩溃平台 | 不接第三方 SDK；使用脱敏服务日志和 Xcode 诊断 | 指标 PRD、采集清单、数据地域、用户同意与供应商 DPA |
| 穿搭推荐模型 | 不进入记账/出行 P0 | 独立 PRD、图片权限、模型成本、内容安全和隐私方案 |

任何待决项目在确认前都必须通过接口隔离，不得把某家云厂商 SDK 或凭据写入领域层。

## 版本与变更策略

- 精确版本是首次实现基线；安全修复可以通过聚焦的依赖升级 PR 更新本文与锁文件。
- Xcode、Swift language mode、最低 iOS、OpenAPI minor、PostgreSQL major、GRDB major 或云供应商变化属于架构变更，必须新增或更新 design 文档并说明迁移与回滚。
- 每月检查安全公告，每季度评估补丁升级；不在功能 PR 中顺手升级无关 major/minor。
- `Package.resolved`、`go.mod`、`go.sum`、OCI image digest 和 CI 工具版本必须可重现；禁止依赖 `latest` tag 进入发布链路。
- 当本文与 README 的简述冲突时，以本文和当前用户明确要求为准，并同步修正文档漂移。
