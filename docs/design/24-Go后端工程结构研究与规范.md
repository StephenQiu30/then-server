# Go 后端工程结构研究与规范

## 状态与目标

- 状态：approved / implemented
- 日期：2026-09-16
- 范围：`then-server/backend`
- 目标：用成熟 Go 项目的共同约束固定可执行入口、业务包、技术适配器和测试边界，替代原先全局 `model/service/repository/transport` 大包。

Go 没有 Java Spring 式官方 MVC/MVVC 目录标准。Go 的编译单元是 package，架构边界必须通过 import 方向、`internal` 可见性和测试约束表达。当前采用“模块化单体 + 领域化 application + ports/adapters”，保留一个 module、一个 binary 和一个 OCI 镜像。

## 一手资料与成熟项目对照

| 来源 | 观察到的真实结构 | 本项目采用 | 不照搬的内容 |
| --- | --- | --- | --- |
| [Go 官方 module layout](https://go.dev/doc/modules/layout) | server 项目可用 `internal` 保存私有逻辑，并用 `cmd` 保存命令 | `cmd/main.go`、`internal/*` | 官方示例不是完整企业脚手架 |
| [Go spec: program execution](https://go.dev/ref/spec#Program_execution) | 可执行程序由含 `main` 的 main package 与依赖链接 | command 保持薄入口 | 不把业务初始化留在 main package |
| [Go testing](https://pkg.go.dev/testing) / [Add a test](https://go.dev/doc/tutorial/add-a-test) | `_test.go` 由 `go test` 单独编译，通常与被测 package 同目录 | 单元/契约测试继续包内共址 | 不按 Java 习惯搬走全部单元测试 |
| [Kubernetes kube-apiserver](https://github.com/kubernetes/kubernetes/blob/master/cmd/kube-apiserver/apiserver.go) | `cmd` main 创建 app command、运行并返回退出码；实际工作在 app 包 | command → bootstrap | 不引入 Cobra、options 树和 Kubernetes 规模设施 |
| [Grafana services](https://github.com/grafana/grafana/tree/main/pkg/services) | accesscontrol、annotations、user 等按业务领域拆包 | application 按 account/privacy/wardrobe/outfitplan/wearevent/media 拆包 | 不引入 Wire 或 Grafana 的公共 `pkg` 面积 |
| [Grafana user domain](https://github.com/grafana/grafana/tree/main/pkg/services/user) | model、合同、实现和 `_test.go` 围绕同一领域组织 | 领域文件语义化命名，测试跟随 package | 当前不增加 impl/testutil 子包，直到出现真实复用 |
| [Prometheus command](https://github.com/prometheus/prometheus/blob/main/cmd/prometheus/main.go) | binary 位于 `cmd/prometheus`，业务由各专门 package 提供 | `cmd/<binary>` 命名 | 不复制其大型 main；本项目用 bootstrap 控制增长 |
| [Grafana Loki commands](https://github.com/grafana/loki/tree/main/cmd) | 多个交付程序各占一个 cmd 子目录 | 当前只有一个真实 binary，入口直接放在 `cmd/main.go` | 增加第二个交付程序时再拆为命名子目录 |
| [CloudWeGo biz-demo](https://github.com/cloudwego/biz-demo) | handler/service/dal 职责分离，示例按业务服务组织 | 保留协议、用例、持久化职责隔离 | 不引入 IDL 生成、多服务或 RPC |

`golang-standards/project-layout` 是社区模板，不是 Go 官方标准；它只能用于理解常见名称，不能作为本项目增加空 `pkg/api/config/scripts` 目录的依据。

## 固定目录

```text
backend/
├── cmd/
│   └── then-server/
│       └── main.go                 # 日志、bootstrap.Run、退出码
├── internal/
│   ├── bootstrap/
│   │   └── application.go          # 唯一 composition root 与生命周期
│   ├── domain/                     # 纯类型、状态、不变量、稳定错误
│   ├── application/
│   │   ├── account/
│   │   ├── privacy/
│   │   ├── wardrobe/
│   │   ├── outfitplan/
│   │   ├── wearevent/
│   │   ├── media/
│   │   └── mediaworker/
│   ├── adapter/
│   │   ├── httpapi/                # Gin/Huma、DTO、Cookie、OpenAPI
│   │   ├── postgres/               # GORM record、查询、事务、AutoMigrate
│   │   ├── objectstore/            # MinIO
│   │   └── messagequeue/           # RabbitMQ
│   └── platform/                   # config、连接和通用进程设施
├── tests/
│   ├── services/                   # 本机真实依赖
│   ├── integration/                # 实际 binary + Testcontainers
│   ├── container/                  # 已构建 OCI 镜像
│   └── internal/                   # 外部 suite 私有夹具
└── architecture_test.go
```

## 依赖合同

```text
cmd → bootstrap
bootstrap       → application + adapter + platform
application     → domain
adapter         → domain
domain          → Go 标准库
```

- application 定义自己消费的 Repository/ObjectStore/Broker 最小 port；具体实现只在 bootstrap 注入。
- domain 和 application 不导入 Gin、Huma、GORM、Redis、MinIO、RabbitMQ 或 Testcontainers。
- httpapi 不导入 GORM/数据库驱动/消息/对象 SDK；postgres 不导入 Gin/Huma。
- command 不直接创建数据库、router 或 worker。
- 不建立 `utils`、`common`、BaseRepository、service locator 或全局可变容器。

`architecture_test.go` 解析 Go import 并阻止以上方向回退。新增跨层依赖必须先修改本设计和架构测试，不能通过移动文件或接口别名规避。

## 测试归属

- 纯规则、application use case、HTTP/OpenAPI 合同继续使用包内 `_test.go`。它们不进入生产 binary，这符合 Go 工具链而不是业务与测试混编。
- `tests/services` 连接本机 loopback PostgreSQL/Redis/MinIO/RabbitMQ。
- `tests/integration` 构建 `./cmd` 并在隔离依赖上运行真实进程。
- `tests/container` 只验收显式提供的本地镜像。
- `tests/` 根目录禁止 Go 文件；suite 必须使用与目录同名的 build tag。

## 变更规则

新增业务能力先判断归属领域：已有领域就在其 application package 增加语义文件；新领域只有在拥有独立状态、规则和 API 时才建目录。新增 SDK 进入对应 adapter；跨领域共享只在出现两个真实消费者并能给出稳定语义后提取，禁止先建 common。

当前处于无历史数据开发阶段，目录迁移不提供旧 import 兼容 alias。API、数据库表名和运行时配置合同保持不变。
