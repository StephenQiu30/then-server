# Go 后端工程结构研究与规范

## 状态与目标

- 状态：approved / implemented
- 日期：2026-09-16
- 范围：`then-server/backend`
- 目标：用 Go 官方约束和成熟项目的真实结构固定命令入口、业务 package、技术适配器和测试边界，避免 Java 目录照搬、全局 model/domain 大包与无所有权的 common。

Go 没有官方 MVC、MVVM 或“企业标准目录”。Go 的编译与封装边界是 package；有效架构必须由目录、import 方向、`internal` 可见性与自动化测试共同表达。`golang-standards/project-layout` 明确说明自己是社区项目且结构不具强制性，因此不能作为“大厂标准”直接复制。

## 调研证据

本轮使用 GitHub、Firecrawl Developer Index 与 Context7 交叉核对源码和官方文档。结论只采用一手文档、仓库源码或维护者的真实重构记录。

| 来源 | 可验证事实 | 对本项目的约束 |
| --- | --- | --- |
| [Go 官方：Organizing a Go module](https://go.dev/doc/modules/layout) | server 项目建议将命令集中在 `cmd`，实现逻辑放在 `internal`；官方示例使用 `cmd/api-server` | 使用 `cmd/then-server/main.go`，目录名与交付二进制一致 |
| [Go 1.4 internal packages](https://go.dev/doc/go1.4#internalpackages) | `internal` 的导入限制由 Go 工具链执行 | 非公共服务实现放在 `internal` |
| [Kubernetes kube-apiserver](https://github.com/kubernetes/kubernetes/blob/master/cmd/kube-apiserver/apiserver.go) | `main` 只创建 command、运行并返回退出码 | `main` 只创建 logger 并委托 bootstrap |
| [GitHub CLI](https://github.com/cli/cli/blob/trunk/cmd/gh/main.go) | `cmd/gh/main.go` 只调用 `internal/ghcmd.Main` | 命令入口不连接数据库、不注册路由 |
| [CockroachDB 入口](https://github.com/cockroachdb/cockroach/blob/master/pkg/cmd/cockroach/main.go) | `main` 只委托 `cli.Main`，命令目录以二进制命名 | 不使用含糊的 `cmd/main.go` |
| [CockroachDB server 拆包记录](https://github.com/cockroachdb/cockroach/issues/81109) | 超大 package 会成为依赖图和增量构建瓶颈 | 不再扩大全局 `domain`，业务归属领域 package |
| [Grafana services](https://github.com/grafana/grafana/tree/main/pkg/services) | 服务按 user、accesscontrol、annotations 等业务能力拆包 | application 按 account、wardrobe、diary、community 拆分 |
| [Grafana store split](https://github.com/grafana/grafana/pull/50727) | API、service 与 store 围绕具体领域拆分 | repository 文件保持领域语义 |
| [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md#package-names) | package 名使用小写、无下划线并避免含糊名称 | 使用 `outfitplan`、`wearevent`、`httpapi` |
| [CloudWeGo biz-demo](https://github.com/cloudwego/biz-demo) | 字节开源业务示例区分 handler、service、dal | 采用职责分离思想，不引入 Kitex/Hertz 生成代码与微服务拓扑 |
| [Kratos layout](https://github.com/go-kratos/kratos-layout) | 模板区分 `cmd/server`、service、biz、data | 采用命名 command 和单向分层，不引入 protobuf、Wire、第二套 OpenAPI |
| [Go testing](https://pkg.go.dev/testing) | `_test.go` 由 `go test` 单独编译，通常与被测 package 共址 | 单元测试包内；真实依赖、进程和镜像测试放在 `tests` |

这些项目的具体树形并不相同。共同标准是薄入口、按职责或能力形成 package、接口靠近消费方、依赖方向可检查、测试层级明确。目录名称只是表达这些约束的手段。

## 决策

当前采用“模块化单体 + 业务能力 package + ports/adapters”：

1. `cmd/then-server/main.go` 是唯一交付入口，`APP_ROLE=api|worker|all` 仍由同一 binary 选择。
2. 删除全局 `internal/domain`。领域模型、稳定错误、规则、用例和该用例消费的最小 port 放入同一个 `internal/application/<feature>` package。
3. 跨业务依赖使用显式白名单，禁止任意横向导入。
4. Gin/Huma、GORM/PostgreSQL、MinIO、RabbitMQ 保持外侧 adapter；bootstrap 是唯一 composition root。
5. PostgreSQL record 存在跨领域外键和事务，当前保留一个 `adapter/postgres` package 并按语义文件拆分；只有出现真实独立边界时才增加子 package。
6. 不建立 `controller/dao/entity` 镜像树，不增加 `pkg`、`common`、`utils`、BaseRepository、service locator、DI 框架或第二个 Go module。

## 固定目录

```text
backend/
├── cmd/then-server/main.go
├── internal/
│   ├── bootstrap/
│   ├── application/{account,privacy,wardrobe,outfitplan,wearevent,diary,community,media,mediaworker}/
│   ├── adapter/{httpapi,postgres,objectstore,messagequeue}/
│   └── platform/{config,database,httpserver,ratelimit}/
├── tests/{services,integration,container,internal}/
└── architecture_test.go
```

每个业务 package 使用语义文件：

```text
application/wardrobe/
├── model.go
├── wardrobe.go
├── authenticator.go
└── *_test.go
```

不创建只有一两个文件的机械 `model/service/repository` 子目录；当一个职责需要独立依赖边界时再成为 package。

## 依赖合同

```text
cmd/then-server → bootstrap
bootstrap       → application + adapter + platform
adapter         → application
application     → 标准库 + 批准的更基础业务 package
```

| package | 可导入的业务 package |
| --- | --- |
| `account` | 无 |
| `privacy` | `account` |
| `wardrobe` | `account` |
| `outfitplan` | `account`、`wardrobe` |
| `wearevent` | `account`、`outfitplan` |
| `diary` | `account` |
| `community` | `account` |
| `media` | `account` |
| `mediaworker` | `media` |

`architecture_test.go` 检查顶层依赖、业务白名单、框架隔离、命令薄入口和测试 suite 布局。新增 import 边必须先更新 Design，不能通过别名包或 service locator 绕过。

## 测试边界

- 纯规则、application use case、HTTP/OpenAPI 合同使用包内 `_test.go`；Go 工具链不会将其编入生产 binary。
- 只通过导出 API 验证的测试优先使用外部测试 package；确需验证未导出不变量的精确单元测试可以使用同 package。
- `tests/services` 连接本机 loopback PostgreSQL、Redis、MinIO、RabbitMQ。
- `tests/integration` 构建 `./cmd/then-server` 并在隔离依赖上运行真实进程。
- `tests/container` 验收已构建 OCI 镜像。
- `tests/internal` 只保存上述 suite 共享的测试基础设施；生产代码禁止导入它。

当前处于无历史数据开发阶段，目录迁移不保留旧 import alias。HTTP 路径、JSON、数据库表名和运行时配置合同保持不变。
